# TreeGov — Phase 3.3 design: population categories

**Purpose.** This document defines the design of population-category support (Phase 3.3) before any code is written. It is the reference for the implementation sub-phases 3.3.a through 3.3.e, and the audit trail for the design decisions taken on 11/10/2026.

**Audience.** The project author, future maintainers, and any MRM reviewer who needs to understand how population-level exclusions are handled end-to-end.

**Status.** Approved. Implementation sub-phases 3.3.a through 3.3.e follow this design. Any deviation discovered during implementation is recorded in `docs/audit_log.md` and reflected back into this document.

**Companion documents.**
- `docs/design_decisions.md` — the pre-existing implementation decisions (Phases 0 to 3.2) that this design must respect.
- `docs/methodology.md` — the mathematical formulas.
- `docs/roadmap.md` — the phase plan.
- `docs/3.1_design_multiclass.md` — reference for style and structure (multiclass design, closed 09/10/2026).

**Historical note.** An earlier design document ("v2 de 3.2", the sample-weighting design) lived only in a chat session and was never saved to `docs/`. References in other documents to "§5.3 B4", "§1bis.2" or "§B8" point to that ephemeral document, not to a file. This Phase 3.3 design uses `docs/3.1_design_multiclass.md` as its only stylistic template.

## §0. Scope and objective

### 0.1 What 3.3 delivers

Phase 3.3 introduces **population categories**: an optional auxiliary CSV column that labels each row with a *reason for exclusion* (e.g. `INDET`, `INSUFFICIENT`, `NO_PERF`). Rows whose label is not in a user-declared set of OK values are excluded from:

- the stratified train/test partition,
- the train-only imputer fit,
- the tree builder input,
- the OOS evaluation (via exclusion before `Session.evaluate_oos`),
- the OOT evaluation and PSI/CSI computation.

Excluded rows are counted and reported with a per-reason breakdown, at both the development-dataset level (train+test) and the OOT-cohort level. They appear in `SessionState` and in the OOT DTO, never silently dropped.

The feature is inspired by the real-world practice of credit bureaus that flag accounts as indeterminate, insufficient, or with no performance history. It is domain-neutral: TreeGov does not impose the naming of the categories, nor their semantics.

### 0.2 What 3.3 does NOT deliver

- **Per-predictor missingness categories.** The population column is a row-level label, not a per-predictor attribute. Missing values inside predictors continue to be handled by `TrainOnlyImputer` (`docs/methodology.md` §5) and by the engines' dropna policies.
- **Automatic detection of "why" a row is excluded.** The reason is whatever the analyst encoded in the CSV. TreeGov does not infer it.
- **A separate model per population category.** Excluded rows are not modelled; they are excluded entirely.
- **A "champion-challenger" of the exclusion policy.** The policy is fixed at `fix_spec` time; changing it requires a new session.
- **GUI display of the excluded rows themselves.** Only their counts and breakdowns are surfaced. Inspecting individual excluded rows remains a CSV-level operation.
- **Retroactive exclusion.** The population column must exist in the CSV loaded by `load_dataset`. It cannot be derived or added after the fact.

### 0.3 Why this scope

The scope is deliberately narrow to keep 3.3 auditable as a single unit. Population categories touch the Session state, the partition logic, the OOT loading path, the DTOs, the wizard, the i18n layer, and the fingerprint. Each of those is a distinct audit surface. Combining 3.3 with, say, multiclass metrics (3.5) or the CRT/QUEST multiclass work (3.4) would multiply the audit surface.

The design deliberately mirrors the sample-weighting design (Phase 3.2) in structure: an optional auxiliary CSV column, declared in `fix_spec`, propagated through the Session, recorded in the fingerprint, exposed in the wizard. Consistency with 3.2 reduces the conceptual load for the maintainer and reduces the "new pattern" surface for the auditor.

## §1. Data model changes

### 1.1 `SessionState` new fields

`SessionState` (frozen dataclass in `backend_v3/session_state.py`) gains the following fields, all defaulted so that the "empty" state remains constructible with no arguments:

    population_col: str | None = None
    population_ok_values: tuple[str, ...] = ()
    n_excluded_population: int = 0
    population_breakdown: tuple[tuple[str, int], ...] = ()
    n_excluded_population_oot: int = 0
    population_breakdown_oot: tuple[tuple[str, int], ...] = ()

Semantics:

- `population_col`: name of the CSV column that carries the population label; `None` before `fix_spec` and when the session is not population-filtered.
- `population_ok_values`: the whitelist declared by the analyst at `fix_spec` time. **Every value not in this tuple is treated as an exclusion reason** (§1bis.2).
- `n_excluded_population`: number of rows of the **development dataset** (the CSV loaded by `load_dataset`) excluded before the partition. Development-level count, not per-partition.
- `population_breakdown`: tuple of `(value, count)` pairs, one per distinct non-OK value observed in the development dataset, ordered by descending count and then by ascending value (deterministic).
- `n_excluded_population_oot`: analogous to `n_excluded_population`, for the OOT cohort loaded by `load_oot`.
- `population_breakdown_oot`: analogous to `population_breakdown`, for the OOT cohort.

All fields are hashable (tuples, not lists) so that `SessionState` remains usable in `replace()` transitions and comparable in tests.

**Naming rationale.** The `_oot` suffix keeps the OOT counts distinct from the development counts. There is no per-partition split of the development counts because the exclusion happens **before** the partition: whatever is excluded is excluded from both train and test at once.

### 1.2 `Session` new caches

`Session.__init__` gains two private attributes, initialized to `None`, analogous to `_w_col` from Phase 3.2:

    self._pop_col: str | None = None
    self._pop_ok_values: tuple[str, ...] | None = None

Rationale: `fix_spec` runs before `partition`/`load_oot`, but the CSV is read once in `load_dataset`. Keeping the population column name and OK values as Session attributes (rather than as `SessionState` fields only) mirrors the existing pattern for `_w_col` and lets `reset_to_data_loaded` clear them explicitly.

`reset_to_data_loaded` gains two reset lines:

    self._pop_col = None
    self._pop_ok_values = None

**Explicit callout.** These two caches are new and MUST be added to both `Session.__init__` and `Session.reset_to_data_loaded`. Omitting either from `reset_to_data_loaded` would leave the session in a half-configured state after the GUI reopens the wizard over the same dataset.

### 1.3 `train_idx` / `test_idx` semantics with population filter

**Decision.** `train_idx` and `test_idx` remain **positions relative to the original `_df`** (the CSV as loaded by `load_dataset`), not positions relative to a filtered view.

**Consequences.**

1. `train_idx ∪ test_idx` is no longer `range(N)` when the population filter is active. The complement is exactly the set of excluded rows, whose size equals `n_excluded_population` and whose breakdown equals `population_breakdown`.
2. `X.iloc[idx_tr]` continues to work unchanged: it selects rows by original position.
3. Auditability: any external reference to "row 42 of the CSV" remains valid across the session lifecycle. A row excluded by the population filter is still uniquely identified by its CSV index.
4. When the population filter is not active (`population_col is None`), `train_idx ∪ test_idx = range(N)` as before. Invariant C1 (see §9) is preserved.

**Documented semantic change.** Before 3.3, `train_idx ∪ test_idx` always covered all rows of the CSV. After 3.3, it covers only the OK rows when the filter is declared. This is a **documented breaking change** on the meaning of the union, not on the type or on the non-filtered case. Tests that assert `len(train_idx) + len(test_idx) == N` must adapt to `len(train_idx) + len(test_idx) + n_excluded_population == N` when the filter is declared, or add `population_col=None` to the fixture to keep the pre-3.3 semantics.

**No new field.** The design does not add a `train_idx_population` or similar. The complement is derivable and cheap.

## §1bis. Population column and OK semantics

This section is the conceptual core of the design. It defines what "OK" means and why the semantics are fail-fast.

### 1bis.1 The population column is optional

The population column is **optional**. If `fix_spec` is called with `population_col=None` (the default), the session behaves exactly as before Phase 3.3. Invariant C1 (see §9) is preserved: with no population column declared, every numeric result, every fingerprint, and every report is bit-identical to the pre-3.3 behaviour.

Mirrors `weight_col=None` from Phase 3.2: the feature is an opt-in.

### 1bis.2 OK values are declared explicitly; everything else excludes

**Decision.** The analyst declares an explicit whitelist of OK values at `fix_spec` time. Any row whose population value is **not** in that whitelist is treated as an exclusion reason, and its value is recorded verbatim in the breakdown.

**Rationale.** This is the fail-fast, MRM-compatible semantics. It is the opposite of a blacklist ("exclude these categories, include everything else"), which would silently include any new value that appeared in the CSV.

Two consequences, both intentional:

1. **A new value in the CSV is never silently included.** If a data refresh introduces `STATUS="NEW"` and the analyst never declared it OK, those rows are excluded and reported. The analyst sees the breakdown and decides.
2. **A typo in the whitelist is visible.** If the analyst declares `("OKk",)` instead of `("OK",)`, every row is excluded and `fix_spec` fails on the `K_ok >= 2` check (§1ter.1). Fail-fast.

Mirrors the principle in `docs/design_decisions.md` §0.3 ("MRM as an explicit choice, not an imposition"): the analyst is the only one who knows which values are legitimate for the population.

### 1bis.3 Fail-fast in both directions

The design fails fast on both sides of the filter:

- **Exclusion side.** No row is silently included without an OK value. Every non-OK row is counted and its value recorded.
- **Inclusion side.** No row is silently excluded without appearing in the breakdown. The breakdown is a complete partition of the excluded set, never a summary.

This is the "no grey zones" rule of the project (`docs/design_decisions.md`, `.treegovrules` §"Mandatory documentation") applied to the population filter.

### 1bis.4 No NaN in the population column

`fix_spec` rejects the population column if it contains any NaN value. Rationale: a NaN is a missing label, which is ambiguous between "exclude because we don't know" and "include because we don't care". Forcing the analyst to encode one or the other as a string removes the ambiguity. This mirrors `weight_col`'s no-NaN rule from Phase 3.2.

If the analyst legitimately wants to exclude rows with missing labels, they must encode the missingness as a string (e.g. `"INDET"` or `"MISSING"`) and either include it in `ok_values` (to keep the rows) or leave it out (to exclude them and see it in the breakdown).

### 1bis.5 Fingerprint records the choice

The `params_fingerprint` payload (see §6) gains two entries:

    "population_col": <str | None>,
    "population_ok_values": <tuple[str, ...]>,

Two trees trained on the same data with the same engine and the same hyperparameters but with **different OK whitelists** do NOT share a fingerprint. This is the MRM evidence that the OK choice was explicit: an auditor reading the fingerprint can reconstruct exactly which rows fed the model.

The fingerprint does **not** include `n_excluded_population` or `population_breakdown`: those are data-dependent, not configuration-dependent, and would break the "same inputs → same fingerprint" invariant across CSVs with identical structure but different exclusion counts.

### 1bis.6 `describe_population_column` returns observed values

`Session` gains a public read-only method, analogous to `describe_target` (Phase 3.1.e) and `describe_weight_column` (Phase 3.2.h):

    def describe_population_column(self, col: str) -> dict:
        """Read-only profile of a candidate population column.

        Returns
        -------
        dict with keys:
            "exists": bool — the column is in the dataset.
            "n": int — number of rows (0 if the column does not exist).
            "values": tuple[tuple[str, int], ...] — (value, count)
                pairs for every observed distinct value, ordered by
                descending count then ascending value (deterministic).
                Empty tuple if the column does not exist or is empty.
        """

Rationale. The wizard needs the observed values **and their counts** to populate the "population categories" table (§4). The analyst then marks which values are OK. Without the observed values in the DTO, the wizard would need to expose `_df` to the frontend, violating the clean room.

The signature deliberately mirrors `describe_target` (which returns `{value: count}`), but adds `exists` and `n` from `describe_weight_column`, to keep both patterns available in one call.

**NaN handling.** If the column contains NaN, `describe_population_column` still returns a profile, but `fix_spec` will reject it (§1bis.4). The DTO reports NaN as the string `"<NaN>"` (a sentinel), so the wizard can surface the problem visually without crashing.

## §1ter. Filter application points

The filter is applied at exactly three points in the Session lifecycle. Everywhere else, the row set has already been filtered.

### 1ter.1 In `fix_spec`: validation only

`fix_spec` gains two new keyword-only parameters:

    population_col: str | None = None,
    population_ok_values: tuple[str, ...] | None = None,

Validation rules (all fail-fast, atomic — no partial state change on failure):

1. If `population_col is None`, then `population_ok_values` must also be `None` (default). The session is not population-filtered.
2. If `population_col is not None`:
   - the column must exist in `_df`;
   - the column must not be the target;
   - the column must not be a declared predictor;
   - the column must not contain any NaN value;
   - `population_ok_values` must be a non-empty tuple of non-empty strings;
   - after applying the filter (`df[col].isin(ok_values)`), the number of remaining rows must be `>= 2 * min(K, ...)` for the target to remain classifiable. Specifically:
     - `K_ok = len(sorted(pd.unique(df_ok[target])))` must be `>= 2`;
     - if `K_ok < 2`, `ValueError` naming the observed K_ok and the K of the full dataset (to help the analyst see the cause).

If any class observed in the **full** dataset is absent from the **filtered** dataset, a `WARNING` is logged, naming the class and its count in the full dataset. The class is **not** added to `target_classes`. The analyst sees the warning and knows a class was dropped by the filter.

State changes (all atomic, applied only if every validation passes):

- `self._pop_col = population_col`
- `self._pop_ok_values = population_ok_values` (or `()` if None)
- `SessionState.population_col = population_col`
- `SessionState.population_ok_values = population_ok_values or ()`

The event log entry for `fix_spec` gains a suffix `|population_col=<name>,ok=<n>` where `<n>` is the number of OK values, so the audit trail records the choice.

### 1ter.2 In `partition`: filtering + imputer + stratification

`Session.partition` is the only method that reads the population filter to compute `_X_train`/`_y_train`/`_X_test`/`_y_test`. The flow becomes:

1. Compute the OK mask from `_df[self._pop_col].isin(self._pop_ok_values)` (if the column is declared; otherwise the mask is all-True).
2. Compute `n_excluded_population = int((~ok_mask).sum())` and `population_breakdown` = tuple of `(value, count)` pairs over the non-OK rows, ordered deterministically.
3. Compute the indices of OK rows: `ok_indices = np.flatnonzero(ok_mask)`.
4. Pass `y[ok_indices]` to `stratified_split`. The split returns positions **relative to `ok_indices`**; map them back to positions relative to `_df` via `ok_indices[idx_rel]`. This yields `train_idx` and `test_idx` as positions relative to `_df` (§1.3).
5. Build `X_train`, `X_test`, `y_train`, `y_test` from the mapped indices, exactly as before.
6. Fit the imputer on `X_train` (already filtered). Transform train and test.
7. Weights (`weight_col` from Phase 3.2) are sliced via the mapped indices, exactly as before.
8. Commit the transition with the new `SessionState` fields: `n_excluded_population`, `population_breakdown`.
9. Event log entry gains `|population_col=<name>` and `|excluded=<n>`.

**Invariant.** If `population_col is None`, the mask is all-True, `n_excluded_population == 0`, `population_breakdown == ()`, and the entire flow is bit-identical to the pre-3.3 behaviour.

**Stratified split contract.** `stratified_split` is not modified in 3.3. It receives the filtered `y` and behaves exactly as before. The "filtering happens upstream" pattern keeps the split module free of population concepts.

### 1ter.3 In `load_oot`: filtering + per-cohort breakdown

`Session.load_oot` is the only method that reads the population filter on the OOT cohort. The flow becomes:

1. If `population_col is not None`, the OOT CSV must include the column. Absent → `ValueError` naming the missing column.
2. Compute the OK mask on the OOT rows.
3. Compute `n_excluded_population_oot` and `population_breakdown_oot` analogously to `partition`.
4. Rows not OK are excluded from `_X_oot` and `_y_oot`.
5. If `weight_col` is also declared, its OOT weights are sliced to the OK rows only.
6. Commit the transition with the two new OOT counts.
7. Event log entry gains `|population_col=<name>,excluded_oot=<n>`.

**Interaction with the existing OOT n_excluded.** Phase 1.3 already counts rows that could not be **routed** through the tree (`unseen_policy="exclude"`) as `n_excluded` in `OOTReport`. Phase 3.3 adds a **different** exclusion: rows that never entered the OOT cache because of the population filter. These two counts are orthogonal and must be kept distinct in the DTO (§5.4).

### 1ter.4 In `reset_to_data_loaded`: clear caches

`reset_to_data_loaded` clears `self._pop_col` and `self._pop_ok_values` alongside `_w_col`. See §1.2.

## §2. Engine changes — none

None of the four engines (CHAID, CHAID_EXHAUSTIVE, C&RT, QUEST) is modified. The population filter is applied upstream of the engines, at the Session layer. Engines never see excluded rows.

This mirrors the "filtering happens upstream" pattern of the anti-leakage imputer: the engine receives already-clean data.

## §3. TreeBuilder changes — fingerprint only

`TreeBuilder.__init__` gains two keyword-only parameters, purely for fingerprint traceability:

    population_col: str | None = None,
    population_ok_values: tuple[str, ...] = (),

Neither parameter is used numerically. They enter the `params_fingerprint` payload (§6). The parameter names match the `SessionState` field names for symmetry.

No other change to `tree_builder.py`. The `TreeNode`/`TreeModel` invariants are unchanged. `w_events` from Phase 3.2 continues to be informative-only.

## §4. Session and SessionState changes

### 4.1 `Session.__init__`

Two new private attributes (§1.2):

    self._pop_col: str | None = None
    self._pop_ok_values: tuple[str, ...] | None = None

### 4.2 `Session.fix_spec`

New keyword-only parameters:

    population_col: str | None = None,
    population_ok_values: tuple[str, ...] | None = None,

Behavior: validation and state changes per §1ter.1.

### 4.3 `Session.partition`

Reads `self._pop_col` and `self._pop_ok_values`, filters the DataFrame, computes `n_excluded_population` and `population_breakdown`, and maps the split indices back to original positions. Flow per §1ter.2.

### 4.4 `Session.load_oot`

Reads `self._pop_col` and `self._pop_ok_values`, requires the column in the OOT CSV, filters the OOT rows, computes the OOT counts, and slices `_X_oot`/`_y_oot`/`_w_oot`. Flow per §1ter.3.

### 4.5 `Session.reset_to_data_loaded`

Adds two reset lines (§1.2, §1ter.4).

### 4.6 `Session.describe_population_column`

New public method per §1bis.6.

### 4.7 `Session.get_oos_oot_report`

Extended: the returned DTO gains keys `oot.n_excluded_population` and `oot.population_breakdown`. The existing `oot.n_excluded` is **renamed** to `oot.n_excluded_routing` (§5.4).

### 4.8 `Session.get_gains_table` and `get_classification_matrix`

Unchanged signatures. The population filter is transparent to these methods because the caches `_X_train`/`_X_test`/`_X_oot` are already filtered. `n_excluded` inside `GainsTableResult` and `ClassificationMatrix` continues to mean "rows unroutable" and is independent of the population filter.

### 4.9 `SessionState` field addition

Per §1.1.

## §5. Downstream changes

### 5.1 `validation.py` — no change

`predict_pd`, `predict_leaf_assignment`, `compute_oos_metrics` are unchanged. They receive already-filtered inputs.

### 5.2 `reporting.py` — no change

`build_gains_table`, `build_classification_matrix`, and the `GainsRow`/`GainsTableResult`/`ClassificationMatrix` dataclasses are unchanged. The `n_excluded` fields keep their "unroutable rows" meaning, which is orthogonal to the population filter.

### 5.3 `stability.py` — no change

`StabilityMonitor` and its DTOs (`PSIReport`, `CSIReport`, `GiniDropReport`, `OOTReport`) are unchanged in their computation. `OOTReport.n_excluded` keeps its "unroutable" meaning.

### 5.4 Naming collision: `n_excluded` vs `n_excluded_population`

**Problem.** Before 3.3, two DTOs already have a field named `n_excluded`:

- `OOTReport.n_excluded` (stability): rows in the OOT cohort that could not be routed through the tree.
- `GainsTableResult.n_excluded` (reporting): rows in a partition that could not be routed.

After 3.3, a new, semantically distinct exclusion exists: "population-excluded rows". Mixing the two in a single `n_excluded` field would destroy auditability.

**Decision.** The two existing `n_excluded` fields keep their names and their "unroutable" meaning. The new population count lives at the **SessionState** level (not in the reporting/stability DTOs) and in the **`get_oos_oot_report` flat DTO** with a distinct name.

**Concrete DTO change.** In `Session.get_oos_oot_report()`'s returned dict:

- `dto["oot"]["n_excluded"]` is **renamed** to `dto["oot"]["n_excluded_routing"]`.
- `dto["oot"]["n_excluded_population"]` is **added** (int).
- `dto["oot"]["population_breakdown"]` is **added** (tuple of `(value, count)`).

This is a **documented breaking change** on the flat DTO only, mirroring how Phase 3.1 broke the flat DTO by changing `pd_final` shape. The inner `OOTReport` dataclass in `stability.py` is unchanged: only the `asdict` flat representation is renamed, to keep the two counts unmistakable in the frontend and in the MRM evidence.

**Alternative considered and rejected.** Adding `n_excluded_population` inside `OOTReport` and keeping the flat name as `n_excluded`. Rejected because the auditor-facing flat DTO would then have an ambiguous key. The rename forces the reader to choose.

## §6. Fingerprint changes

### 6.1 New entries in the fingerprint payload

`TreeBuilder._fingerprint` gains two entries:

    "population_col": <str | None>,
    "population_ok_values": <tuple[str, ...]>,

Rationale per §1bis.5.

### 6.2 Effect on existing fingerprints

Fingerprints computed **before 3.3** will not match fingerprints computed **after 3.3** on the same data with the same hyperparameters, because the payload has changed. This is the same acceptable break as Phase 3.1 (multiclass) and Phase 3.2 (weighting), documented in `audit_log.md`. At v1.0.0a1, no production models exist.

### 6.3 No change to the "same inputs → same fingerprint" invariant

Two sessions with identical data, identical spec, identical engine parameters, and identical `population_col`/`population_ok_values` still produce identical fingerprints, even if their exclusion counts differ across CSVs (the counts are data, not configuration).

## §8. Sub-phase plan

The implementation of Phase 3.3 is divided into **five** sub-phases. Each is auditable as a unit. The choice of 5 (rather than a finer decomposition) is deliberate: the session-level work touches a single file, and consolidating the changes into one sub-phase reduces the prompt count without increasing the audit surface per commit.

| Sub-phase | Scope | Files | Sessions |
|---|---|---|---|
| **3.3.a** | `SessionState` fields; `Session.__init__` caches; `fix_spec`; `partition`; `load_oot`; `reset_to_data_loaded`; `describe_population_column`. | `session_state.py`, tests | 1 |
| **3.3.b** | `TreeBuilder` new keyword-only params; fingerprint payload. | `tree_builder.py`, tests | 1 |
| **3.3.c** | Propagate through `get_oos_oot_report` (rename + new keys). No changes to `validation.py` / `reporting.py` / `stability.py` beyond the flat DTO. | `session_state.py`, tests | 1 |
| **3.3.d** | Wizard: combo, mirror rule, OK-values table, i18n keys. | `wizard.py`, `i18n.py`, `main_window.py`, tests | 1 |
| **3.3.e** | E2E tests; documentation closure. | `tests/`, docs | 1 |

**Total.** 5 sessions.

**Dependency.** Strict linear order: 3.3.a → 3.3.b → 3.3.c → 3.3.d → 3.3.e. Each sub-phase's tests must pass before the next starts.

**Commit boundaries.** Each sub-phase ends with a commit and its `audit_log.md` entry. The phase-closure documentation (roadmap + estado_proyecto + contexto + prompt_para_asistente + design_decisions + methodology, if applicable) happens in 3.3.e, as a single unit, per the "phase closure documentation: never deferred" rule.

## §9. Risks and invariants

### 9.1 Non-negotiable invariants

These must hold at every commit of Phase 3.3:

- **C1 (parity, no filter).** With `population_col=None`, every numeric result, every fingerprint, and every report is bit-identical to the pre-3.3 behaviour. Verified by `test_population_partition_without_filter_c1_parity` and by running the full pre-3.3 test suite unchanged.
- **Idx semantics.** `train_idx` and `test_idx` are positions relative to `_df` (the CSV as loaded), never relative to a filtered view.
- **Complete partition of excluded rows.** The sum of counts in `population_breakdown` equals `n_excluded_population`. No row is counted twice, no row is missed.
- **No NaN in the population column.** `fix_spec` rejects.
- **K_ok >= 2.** `fix_spec` rejects if the filter leaves fewer than two target classes.
- **The full test suite passes.** `python -m pytest tests -q` → all green, at every commit.

### 9.2 Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| 1 | **`train_idx ∪ test_idx` no longer equals `range(N)` when filter is on.** External code or tests that assume the union is total will break. | Medium | Medium | Documented breaking change (§1.3). Tests that need the total set add `population_col=None`. |
| 2 | **Wizard flow becomes longer.** Analyst must declare OK values in addition to all prior steps. | Certain | Low | The population step is conditional: the combo defaults to "(no population filter)". Only analysts who need it see the extra table. |
| 3 | **`n_excluded` name collision.** SessionState, OOTReport, GainsTableResult all have their own "excluded" counts. | Certain | Medium | Explicit naming decision (§5.4): SessionState-level counts use `_population` suffix; the flat DTO renames the existing key to `_routing`. |
| 4 | **Fingerprint change breaks existing cached fingerprints.** | Certain | Low | Documented, alpha-only. Same treatment as 3.1 and 3.2. |
| 5 | **OK whitelist typo silently excludes everything.** The analyst declares `("OKk",)` instead of `("OK",)`. | Low | Low | `fix_spec` fails on K_ok < 2 with a message naming the counts. Fail-fast. |
| 6 | **Population column with NaN slips through.** | Low | Medium | `fix_spec` rejects NaN with a message naming the first offending row. |
| 7 | **`load_oot` with a population column not in the OOT CSV.** | Medium | Low | `ValueError` at `load_oot` naming the missing column. |
| 8 | **Stratified split with tiny OK subset.** The filter leaves, say, 8 rows for a binary target. | Medium | Low | `stratified_split` already enforces its own `n_k >= 2` minimum on the filtered data; the error message names the residual class. |
| 9 | **OOT cohort has a new non-OK value that was never seen in dev.** | Medium | Low | Fail-fast by design: the new value is excluded and appears in `population_breakdown_oot`. The analyst sees it and decides whether to update the OK whitelist in a new session. |

### 9.3 Non-goals (revisited)

- 3.3 does not introduce a way to *change* the OK whitelist without resetting the session. Changing the whitelist requires `reset_to_data_loaded` + `fix_spec` again. This is deliberate: the whitelist is part of the model's identity, and its change is a new model, not a mutation of an existing one.
- 3.3 does not model the excluded rows in any way (no separate tree, no scoring, no profiling). They are excluded, reported, and left aside.
