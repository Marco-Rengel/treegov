# TreeGov — Phase 3.1 design: multiclass support

**Purpose.** This document defines the design of multiclass support
(Phase 3.1) before any code is written. It is the reference for the
implementation sub-phases 3.1.a through 3.1.f, and the audit trail for
the design decisions taken on 04/10/2026.

**Audience.** The project author, future maintainers, and any MRM
reviewer who needs to understand how multiclass targets are handled
end-to-end.

**Status.** Approved — implementation in progress (sub-fases 3.1.a
a 3.1.f). The design is being reconciled with the actual
implementation as sub-phases close; see §2.2 and §4.1 for the
reconciliations applied so far.

**Companion documents.**
- `docs/design_decisions.md` — the pre-existing implementation decisions
  (Phases 0 to 3.0) that this design must respect.
- `docs/methodology.md` — the mathematical formulas.
- `docs/roadmap.md` — the phase plan (Fase 3.1 is the first sub-phase
  of the new Fase 3).

**Domain-neutrality note.** TreeGov is not a credit-risk-only tool.
This document uses domain-neutral language ("class of interest",
"minority class", "event rate") and defers domain-specific labels to
user input. Where a term has a strong academic anchor (e.g., Jeffreys
estimator, Dirichlet prior), the academic reference is used.

---

## §0. Scope and objective

### 0.1 What 3.1 delivers

Phase 3.1 opens multiclass targets in the tree-building pipeline:
- `TreeBuilder` accepts binary **or** multiclass (K ≥ 2) targets.
- `TreeNode` and `TreeModel` expose the per-class probability vector.
- `Session.fix_spec` requires the analyst to specify `target_class`
  and `class_labels` explicitly.
- The wizard (Fase 3.1.e) enforces this configuration and warns if the
  analyst may have chosen the wrong class.
- The `MetricsPanel` (Fase 3.1.f) detects a probable class inversion
  after training and offers a one-click correction.

### 0.2 What 3.1 does NOT deliver

- **Multiclass metrics** (multiclass Gini, KS, HL, confusion matrix
  K×K). Deferred to Fase 3.5.
- **Multiclass support in C&RT and QUEST.** Deferred to Fase 3.4.
- **Sample weighting.** Deferred to Fase 3.2.
- **Special population categories** (Indet / Insufficient / No Perf).
  Deferred to Fase 3.3.
- **Regression targets** (`TargetType.CONTINUOUS`). Deferred to a later
  phase, not yet scheduled.
- **GUI changes beyond the wizard and the inversion alert.** All other
  GUI surfaces (tree viewer, gains table, report panel) remain
  binary-only in 3.1.

### 0.3 Why this scope

The scope is deliberately narrow to make 3.1 auditable as a single
unit. Opening multiclass touches the deepest layer of the model
(TreeBuilder, TreeNode, TreeModel) and every consumer must be checked
for binary assumptions. Combining that with metrics (3.5), additional
engines (3.4), or weighting (3.2) would multiply the audit surface.

## §1. Data model changes

### 1.1 `TreeNode.pd_final`, `TreeNode.pd_jeffreys`, `TreeNode.n_events`

**Current state (as of Phase 3.0):**

    n_events: int         # count of class 1
    pd_jeffreys: float    # (k + 0.5) / (n + 1.0)
    pd_final: float       # max(pd_floor, pd_jeffreys) or pd_jeffreys

**Target state (3.1):**

    n_events: tuple[int, ...]        # counts per class, in internal order
    pd_jeffreys: tuple[float, ...]   # per-class, no floor, sums to 1
    pd_final: tuple[float, ...]      # per-class, floor applied, sums to 1

**Internal order convention.** The vector is ordered so that
`index 0` is always `target_class` (see §1bis.4). This invariant is
enforced by `TreeModel.__post_init__` and by construction in
`TreeBuilder`.

**Backward compatibility (K = 2).** For a binary target with
`target_class = 1`, the vector is `(pd_0, pd_1)` where `pd_1` is the
probability of the class of interest. Consumers that historically read
`node.pd_final` as a scalar now read `node.pd_final[0]`. The numeric
value is **identical** to the pre-3.1 scalar.

### 1.2 `TreeNode.class_labels`

**New field (3.1):**

    class_labels: tuple[str, ...]

- One label per class, same order as `pd_final`.
- Purpose: any consumer that reads `pd_final[c]` can also read
  `class_labels[c]` to know what class `c` represents.
- Immutable (tuple, not list).
- Must satisfy `len(class_labels) == len(pd_final)`.

**Example.** For a binary target with `class_labels = ("Malo", "Bueno")`
and internal order `[target_class=1, other=0]`, `pd_final[0]` is the PD
of "Malo" and `pd_final[1]` is the PD of "Bueno".

### 1.3 `TreeModel.class_labels` and `TreeModel.target_class`

**New fields (3.1):**

    class_labels: tuple[str, ...]
    target_class: int | str          # the analyst's chosen class
    target_class_index: int          # internal index of target_class (always 0)

- `class_labels` mirrors the `TreeNode` field (single source of truth:
  the value lives in `TreeModel` and is propagated to each node).
- `target_class` records the analyst's choice as entered.
- `target_class_index` is always 0 by construction (the invariant is
  enforced in `__post_init__`). It exists for explicitness and
  cross-checking.

**Rationale.** Two trees with the same data but different
`target_class` produce different probability semantics and different
metrics downstream. The `TreeModel` must record which class was
chosen, and the fingerprint must reflect it (§7).

### 1.4 New invariant: `sum(pd_final) == 1`

`TreeModel.__post_init__` will verify, for every node:

    abs(sum(nd.pd_final) - 1.0) <= 1e-12

Failure raises `ValueError` at construction. This prevents silent
numerical drift (e.g., if the floor + renormalization is misapplied).

A second invariant is added:

    len(nd.pd_final) == len(nd.pd_jeffreys) == len(nd.n_events)
                            == len(self.class_labels)

Failure raises `ValueError` with a clear message.

## §1bis. Target class and class labels

This section is the most important of the design: it addresses the
**class inversion problem** that a class of interest silently mishandled
would create (see `docs/design_decisions.md` §0.4 on vocabulary policy
and the motivation for explicit configuration).

### 1bis.1 `target_class` — mandatory, no default

**Signature change.**

    Session.fix_spec(
        self,
        target: str,
        spec: dict[str, PredictorType] | None = None,
        *,
        predictors: Sequence[str] | None = None,
        target_class: int | str,     # OBLIGATORIO, no default
    ) -> SessionState

**Behaviour.**

- If `target_class` is not passed: `TypeError` raised by the Python
  interpreter itself (mandatory positional-by-keyword argument). No
  silent default.
- If `target_class` is not in the observed classes of `target`:
  `ValueError` with a message listing the observed classes.
- The value is stored in `SessionState.target_class`.

**Rationale.** A silent default (typically `1`, or the largest class, or
the last class in sorted order) would produce a model whose metrics are
silently inverted when the analyst's convention differs from the
default. This is a documented problem in software where the "category
of interest" is a default rather than an explicit choice. Making it
mandatory eliminates the risk.

**Reference.** This is the same principle as the
"category of interest" selection found in some statistical environments (e.g., R's `relevel()`), but enforced at the
API level (no reliance on user discipline).

### 1bis.2 `class_labels` — mandatory, no default

**Signature change.**

    Session.fix_spec(
        self,
        target: str,
        spec: dict[str, PredictorType] | None = None,
        *,
        predictors: Sequence[str] | None = None,
        target_class: int | str,
        class_labels: Mapping[int | str, str],   # OBLIGATORIO, no default
    ) -> SessionState

**Behaviour.**

- `class_labels` must be a mapping from every observed class of
  `target` to a human-readable string.
- If the mapping misses any observed class, `ValueError` with the
  missing values listed.
- If the mapping contains values not present in the observed classes,
  `ValueError` with the extra values listed.
- Labels must be non-empty strings. Duplicate labels are allowed but
  produce a `WARNING` in the log (they can make reports ambiguous).

**Rationale.** The report surfaces (gains table, confusion matrix) and
the GUI need a human-readable label for each class. A generic default
("Class 1", "Class 2") would be neutral but unhelpful. Making the
labels mandatory forces the analyst to think about the semantics of
each class. Since `target_class` is already mandatory (1bis.1), adding
`class_labels` is a small extra step.

**Domain-neutrality.** The labels are user input. TreeGov does not
impose "Malo" / "Bueno" or "Default" / "No default". For a biological
dataset, the analyst writes `{0: "Sano", 1: "Enfermo"}`. For a
credit dataset, `{0: "Bueno", 1: "Malo"}`. The tool only enforces that
a label exists.

### 1bis.3 Fingerprint changes

The `params_fingerprint` payload gains three entries:

    "target_class": <int | str>,
    "target_class_index": 0,
    "class_labels": <tuple of str>,

Two trees with the same data and hyperparameters but different
`target_class` will have different fingerprints. This is the evidence
that the choice was explicit.

**Effect on existing models.** Fingerprints computed before 3.1 will
not match fingerprints computed after 3.1 on the same data, because the
payload changes. This is acceptable at this stage (v1.0.0a1 is an
alpha; no production models exist).

### 1bis.4 Internal class ordering

**Convention.** Internally, TreeGov reorders the classes so that
`target_class` is always at index 0.

**Example (binary).**

- Analyst input: `target = "GoodBad"`, values `{0, 1}`,
  `target_class = 1`, `class_labels = {1: "Malo", 0: "Bueno"}`.
- Internal order: `[target_class, other] = [1, 0]`.
- Internal labels: `("Malo", "Bueno")`.
- `pd_final = (pd_malo, pd_bueno)`.

**Example (binary, inverted).**

- Analyst input: same, but `target_class = 0`, `class_labels = {0: "Malo", 1: "Bueno"}`.
- Internal order: `[0, 1]`.
- Internal labels: `("Malo", "Bueno")`.
- `pd_final = (pd_malo, pd_bueno)`.

**Invariant consequence.** Any code that needs "the probability of the
class of interest" reads `pd_final[0]`. This is independent of the
numeric value the analyst used in the data. The inversion risk is
eliminated by construction.

**Non-target classes ordering.** In multiclass (K > 2), the remaining
classes are ordered by ascending code (or ascending sorted value for
string labels). This is deterministic and documented.

## §1ter. Pre-training validation (wizard layer)

The wizard (Fase 3.1.e) is where the analyst configures the model. Three
complementary checks ensure that the class choice is informed and, if
wrong, visible before training starts.

All three checks are **active simultaneously**. They are not
alternatives: each addresses a different failure mode.

### 1ter.1 Value check — only observed classes offered

The class-selection combo **only lists the classes actually observed in
the target column** of the loaded dataset. There is no free-text input.

**Rationale.** Eliminates the possibility of typo or mismatch between
the class value entered and the values present in the data. If the
analyst expects a class that is not in the data, the dataset itself is
misconfigured, not the wizard.

**Consequence.** If the target has 3 observed classes, the combo shows
exactly 3 items. If it has 2, two items. No "Other" or "Custom" option.

### 1ter.2 Counts visible — distribution at a glance

Each option in the combo shows the **class value, its label (editable
by the analyst), and the row count**.

**Example layout (binary):**

    Malo  (1) — 3,450 rows
    Bueno (0) — 6,550 rows

**Example layout (multiclass):**

    Low   (0) — 7,100 rows
    Mid   (1) — 1,850 rows
    High  (2) —   550 rows

**Rationale.** Seeing the counts is the fastest way for the analyst to
notice the shape of the target distribution. It supports check 1ter.3
below: the minority class is usually the class of interest in
phenomena-detection analyses, and the count makes it visible without
running any extra analysis.

### 1ter.3 Minority-class warning — non-blocking, visible

**Trigger.** The analyst selects as `target_class` the **majority
class** of the target.

**Behaviour.** A visible **amber banner** appears in the wizard:

    You have selected the majority class as the class of interest.
    In phenomena-detection analyses, the class of interest is usually
    the minority class (the rare event we want to detect). Verify that
    the class is not inverted.

The Next button **remains enabled** — the analyst can proceed if the
choice is intentional. But the warning is shown until the user leaves
Step 2, and the log records:

    [wizard] target_class=<value> (majority class); warning shown; user continued

**Rationale.** The wizard cannot decide whether the choice is right —
the analyst may have a legitimate reason to model the majority class.
But it can make the choice visible, and it can record that the choice
was made despite the warning. This is the "documented decision"
pattern of MRM: not blocked, but traceable.

**Domain neutrality.** The warning text uses "phenomena-detection
analyses" and "rare event", not "risk", "default", or "credit".
Different domains reinterpret the same logic ("disease detection",
"fraud detection", "anomaly detection").

## §1quater. Post-training alerts (evaluation layer)

Once the model is trained, three signals can indicate that
`target_class` was chosen incorrectly. Detection is automatic; the
analyst is informed but not blocked. A one-click correction is
available.

### 1quater.1 Negative Gini badge

**Trigger.** The `MetricsPanel` (Fase 3.1.f) shows the model's OOS Gini
and observes `gini < 0`.

**Behaviour.** A **red badge** appears in the panel:

    Negative Gini detected. Verify that `target_class` is not inverted.

**Rationale.** A model with a negative Gini on the sample it was
trained on is (almost always) an inverted-class model. There are
exotic exceptions (adversarial construction, deliberately inverse
labels), but for the standard case this is the diagnostic.

### 1quater.2 Decreasing cumulative event rate

**Trigger.** In the gains table (when viewed after 3.5 enables
multiclass metrics), the column `event_rate_cum` **decreases** as rows
are accumulated top-down, instead of increasing.

**Behaviour.** The gains table shows a **red arrow** next to the
column header and the same badge as 1quater.1.

**Rationale.** By construction of the ordering (rows sorted by
ascending PD of `target_class`), the cumulative event rate should
increase as we move toward the higher-PD rows. A decreasing pattern is
the signature of an inverted class.

**Note.** This check is only meaningful once 3.5 delivers multiclass
metrics. In 3.1, the check is documented but not yet wired.

### 1quater.3 Reversal button — one-click correction

**Trigger.** Manual. Shown in the `MetricsPanel` next to the diagnostic
badges.

**Behaviour.** A button labelled:

    Invert target_class and retrain

When pressed:

1. The wizard is not re-opened.
2. The current `Session` is reset to the `DATA_LOADED` state (the
   cached DataFrame is preserved).
3. `Session.fix_spec` is called again with the inverted
   `target_class` and the same `class_labels` (with the two labels
   swapped).
4. `Session.partition` is called again with the same parameters.
5. `Session.train` is called again with the same engine and
   hyperparameters.
6. The metrics panel is refreshed.
7. The action is logged:

        [gui] target_class inverted from <X> to <Y> by user action

**Rationale.** If the analyst's only mistake was the class choice, the
recovery should be a single click, not a full re-run of the wizard.
The rest of the configuration (predictors, engine, hyperparameters,
partition) is preserved verbatim.

**Safety.** The reversal is not automatic. The analyst presses the
button. If they ignore the badge, nothing happens.

## §2. Engine changes

### 2.1 CHAID — no change needed

CHAID (both classic and Exhaustive) already supports multiclass
targets:
- The target variable goes through `pd.crosstab(x, y)` which handles
  any number of classes.
- The χ² statistic is computed on a (c, K) contingency table, with
  degrees of freedom `(r − 1)(K − 1)`.
- The merge logic is agnostic to K.

**No changes to `chaid_engine.py` in 3.1.**

### 2.2 C&RT — blocked at K > 2 in 3.1

`CrtEngine` internally supports multiclass (Gini impurity is defined
for any K). However, opening it in 3.1 without the corresponding
metric work (3.5) and the corresponding QUEST work (3.4) would create
an asymmetric product: CHAID multiclass, CRT binary, QUEST binary.
The user experience would be confusing.

**Decision.** In 3.1, `Session.train` restricts multiclass to the
CHAID family: **CHAID** and **CHAID_EXHAUSTIVE** (both are
`ChaidEngine` instances, one with `exhaustive=True`).
If the user selects C&RT or QUEST with K > 2, a `ValueError` is
raised:

    [session] engine 'CRT' does not support multiclass targets in
    Phase 3.1 (K=3 classes detected). Use CHAID for multiclass, or
    wait for Phase 3.4.

The error message names both CHAID variants as the valid options
for multiclass; C&RT and QUEST are blocked until Phase 3.4.
`CHAID_EXHAUSTIVE` uses the same engine class as `CHAID`, so
allowing it in 3.1 is not an additional engine — it is a
configuration of an already-admitted engine.

**Fase 3.4 removes the restriction.**

### 2.3 QUEST — blocked at K > 2 in 3.1

Same reasoning as C&RT. `QuestEngine` explicitly rejects K > 2 today
(`_prepare` raises `ValueError` when it detects more than 2 classes).
In 3.1 that restriction stands; the error message is refined to point
to Fase 3.4.

## §3. TreeBuilder changes

### 3.1 New parameter `target_class`

`TreeBuilder.__init__` gains a mandatory keyword-only parameter:

    target_class: int | str

- Must be one of the values passed in `y` at `build()` time.
- `build()` raises `ValueError` if `target_class` is not present.

The value is not used numerically; it only drives the **internal class
ordering** (§1bis.4) and the fingerprint (§7).

### 3.2 Jeffreys estimator, multivariate form

**Current (binary).**

    pd_jeffreys = (k + 0.5) / (n + 1.0)

where `k` is the count of the event class and `n` is the node's
population.

**General form (K ≥ 2).**

    pd_jeffreys[c] = (k_c + 0.5) / (n + K * 0.5)

where `k_c` is the count of class `c` in the node, `n` is the node's
population, and `K` is the number of classes in the target.

**Properties.**

- **Sum invariant.** `sum(pd_jeffreys) = (sum(k_c) + K*0.5) / (n + K*0.5) = (n + K*0.5) / (n + K*0.5) = 1`. Exact.
- **Binary consistency.** With `K = 2`, the formula gives:
  `pd_jeffreys[c] = (k_c + 0.5) / (n + 1.0)`, which is exactly the
  binary formula. **Zero change when K = 2.**
- **Prior.** This is the mean of the posterior under a symmetric
  `Dirichlet(0.5, 0.5, ..., 0.5)` prior, the natural multivariate
  extension of the Jeffreys prior for a categorical distribution.

**Citation.** Jeffreys, H. (1946). *An invariant form for the prior
probability in estimation problems*. Proceedings of the Royal Society
of London A, 186(1007), 453-461.

### 3.3 `pd_floor` in K > 2

**Problem.** In binary, `pd_floor` is applied to the class-of-interest
probability, and the other class is derived as `1 - pd_final[0]`. This
keeps the sum at 1.

In multiclass, applying `pd_floor` component-wise and then leaving
values unnormalized would break the sum invariant.

**Decision.** Apply `pd_floor` component-wise, then renormalize:

    pd_temp[c] = max(pd_floor, pd_jeffreys[c])
    pd_final[c] = pd_temp[c] / sum(pd_temp)

**Properties.**

- Sum invariant preserved exactly (up to floating point).
- The floor is a **soft floor** in multiclass: a component is guaranteed
  to be ≥ `pd_floor / sum(pd_temp)`, not exactly `pd_floor`. The
  effective floor depends on the distribution's shape.
- In binary, this reduces to the standard floor behavior: the class of
  interest gets `max(pd_floor, pd_jeffreys[0])`, and the other class
  gets `1 - that`.

**Alternative considered (rejected).** Apply the floor only to the
target class and renormalize. Rejected: it privileges one class in a
way that is not obviously justifiable for multiclass. The component-wise
soft floor is symmetric and neutral.

**Documented in.** `design_decisions.md` §6.4 (updated).

### 3.4 The class-ordering invariant

**Convention.** Internally, the class vector is ordered such that
index 0 corresponds to `target_class`. The remaining classes are
ordered by ascending value (numeric sort for numeric classes, string
sort for string classes).

**Guaranteed by.**

- `TreeBuilder.__init__` computes the ordering once and stores it.
- `build()` uses the ordering when computing `n_events`,
  `pd_jeffreys`, and `pd_final`.
- `TreeModel.__post_init__` verifies that
  `len(pd_final) == len(class_labels) == len(n_events)`.

**Consumer contract.** Any code that reads `pd_final[0]` is reading the
probability of the class of interest. This is the sole convention
consumers need to know.

**Determinism.** Two trees built from the same data with the same
`target_class` will produce identical class orderings and identical
probability vectors. The `params_fingerprint` records the ordering
implicitly through `target_class` and `class_labels`.

## §4. Session and SessionState changes

### 4.1 `Session.fix_spec` gains mandatory parameters

**Signature change.**

    def fix_spec(
        self,
        target: str,
        spec: dict[str, PredictorType] | None = None,
        *,
        predictors: Sequence[str] | None = None,
        target_class: int | str,               # NEW, mandatory
        class_labels: Mapping[int | str, str], # NEW, mandatory
    ) -> SessionState

**Behaviour changes (relative to Phase 3.0).**

- `target_class` must be one of the observed values of the target
  column. Otherwise `ValueError` with the observed classes listed.
- `class_labels` must cover every observed class exactly once. Missed
  or extra keys raise `ValueError` with the offending values listed.
- Both are stored in `SessionState`.
- The existing binary-only validation is preserved for K=2: a
  binary target **must still be encoded as `{0, 1}`**. The
  validation is extended, not relaxed: for K ≥ 3 any encoding is
  accepted; for K = 2 the strict `{0, 1}` encoding is required
  (see below). It remains rejected if K < 2 (a constant target
  has no split value) or if the target contains NaN.

**Reconciliation note (09/10/2026).** The original design said
the binary-only validation would be "relaxed to K >= 2". During
implementation (Pasos 4.1-4.6), it was decided to **preserve the
strict binary encoding `{0, 1}` for K=2** and to **open
multiclass only for K >= 3**. Rationale: the non-negotiable
invariant (§10.1) requires that a binary model with
`target_class=1` be numerically identical to the pre-3.1 model;
that invariant is only guaranteed if the binary encoding stays
`{0, 1}`. For K >= 3, any encoding is accepted because there is
no pre-3.1 behaviour to preserve. This is stricter than the
original design, not more permissive.

**Non-regression guarantee.** For a binary target with
`target_class=1` and `class_labels={0: "Non-event", 1: "Event"}`, the
resulting `SessionState` carries the same class ordering and PD values
as before 3.1. Consumers reading `pd_final[0]` get the same number
they would have read from `pd_final` pre-3.1.

### 4.2 `SessionState` gains `target_class` and `class_labels`

**New fields (frozen, hashable).**

    target_class: int | str | None = None
    class_labels: tuple[tuple[int | str, str], ...] = ()
        # stored as a tuple-of-pairs to remain hashable (frozen dataclass)

- `target_class` is `None` before `fix_spec` is called, and set after.
- `class_labels` is stored as a tuple of (value, label) pairs, sorted
  by value, so that the `SessionState` remains hashable.
- The `Session` class exposes a helper property
  `class_labels_dict` returning the `dict` form for convenience.

**Rationale.** `SessionState` is a frozen dataclass; storing a `dict`
would break hashability. A tuple of pairs is the canonical workaround.

### 4.3 `Session.train` propagates to `TreeBuilder`

**Signature change (logical only).**

The public signature of `Session.train` does not change: it continues
to accept the same arguments. Internally, it:

1. Reads `self._state.target_class` and `self._state.class_labels`.
2. Validates that, for `K > 2`, the chosen engine is CHAID (§2.2 and
   §2.3).
3. Constructs a `TreeBuilder` instance with the new parameters.
4. Calls `builder.build(...)`.

Any attempt to train a multiclass model with a non-CHAID engine raises
`ValueError` with the message from §2.2.

## §5. Downstream changes in 3.1 — blocking vs deferring

### 5.1 `validation.py` — block K > 2 in 3.1

`predict_pd` and `predict_leaf_assignment` (see §6) are adapted to the
new `TreeNode.pd_final` shape. The metric functions
(`compute_oos_metrics`, `OOSMetrics`) **remain binary-only**.

**Behaviour.**

- `predict_pd` returns a 2D array of shape `(n_rows, K)`. The shape
  reflects the number of classes.
- `compute_oos_metrics` raises `ValueError` if called with a K > 2
  probability array:

        [validation] multiclass metrics not implemented in Phase 3.1
        (K=<n> classes detected). Scheduled for Phase 3.5.

- `Session.evaluate_oos` and `Session.evaluate_oot` also raise the
  same error when the model was trained on K > 2 classes.

**Rationale.** Fase 3.1 opens the tree builder; Fase 3.5 opens the
metrics. Keeping the boundary explicit avoids silent partial metrics
that could mislead the analyst.

### 5.2 `reporting.py` — block K > 2 in 3.1

`build_gains_table` and `build_classification_matrix` remain binary.

**Behaviour.** Both functions raise `ValueError` with a message
pointing to Fase 3.5 if called with a model whose
`len(model.class_labels) > 2`.

`Session.get_gains_table` and `Session.get_classification_matrix`
propagate the error.

**Rationale.** Same as 5.1. The gains table has columns (`n_bad`,
`bad_rate`, `lift_cum`) whose meaning is anchored to a binary
target. Extending them to multiclass requires rethinking the report
semantics (which will happen in 3.5).

### 5.3 `stability.py` — block K > 2 in 3.1

PSI (leaf stability) and CSI (covariate stability) are computed on the
leaf distribution and on the covariate distributions. The leaf
distribution is agnostic to the target shape; the covariate CSI is
also target-agnostic.

**However**, the `OOTReport` includes a `Gini Drop` component which
requires binary Gini. Since binary Gini is not computable for K > 2,
`Session.evaluate_oot` must block multiclass targets.

**Behaviour.**

- PSI and CSI computation routines are unchanged.
- `Session.evaluate_oot` raises `ValueError` when the model has
  K > 2 classes.

**Rationale.** PSI/CSI are target-agnostic and could in principle be
computed; Gini Drop is not. Blocking the whole `evaluate_oot` call
keeps the failure mode clear and consistent with §5.1 and §5.2.

**Deferred to 3.5.** A multiclass-aware OOT report.

## §6. `predict_pd` and `predict_leaf_assignment` — new shape

### 6.1 `predict_pd` returns a 2D array

**Current signature (pre-3.1).**

    def predict_pd(
        model: TreeModel, X: pd.DataFrame, *, unseen_policy: str = "error"
    ) -> np.ndarray   # shape (n_rows,), dtype float

**New signature (3.1).**

    def predict_pd(
        model: TreeModel, X: pd.DataFrame, *, unseen_policy: str = "error"
    ) -> np.ndarray   # shape (n_rows, K), dtype float

**Behaviour.**

- For each row, the array holds the K-length PD vector of the leaf
  the row was routed to.
- Rows excluded by `unseen_policy="exclude"` are returned as all-NaN
  rows.
- Rows excluded by `unseen_policy="error"` raise before the array is
  built (unchanged).
- Rows excluded by `unseen_policy="majority"` are routed to the
  majority leaf and receive that leaf's PD vector.

**Consumers.**

- Binary consumers read column 0: `pd_2d[:, 0]` (the class of
  interest).
- Multiclase consumers (in 3.5) read all columns.

### 6.2 `predict_leaf_assignment` unchanged

`predict_leaf_assignment` returns the leaf `node_id` per row, `-1`
for excluded rows. **The function is unchanged**: it does not depend
on K.

### 6.3 Reordering convention propagation

The reordering convention from §1bis.4 is propagated by construction:
`predict_pd` reads the leaf's `pd_final` tuple, which is already
ordered with `target_class` at index 0. No additional reordering is
needed downstream.

**Consumer contract.** `pd_2d[:, 0]` is always the probability of the
class of interest, independent of the numeric value the analyst used
in the data.

## §7. Fingerprint changes

### 7.1 New entries in the fingerprint payload

The payload of `TreeBuilder._fingerprint` gains:

    "target_class": <int | str>,
    "target_class_index": 0,
    "class_labels": <tuple of (value, label) pairs>,
    "n_classes": <int>,

The `spec` entry remains unchanged. The `governance_mode` entry remains
unchanged.

**Consequences.**

- Two trees with the same data, hyperparameters, and predictors but
  different `target_class` produce different fingerprints. This is the
  evidence that the class choice was explicit.
- Two trees with the same data but different `class_labels` produce
  different fingerprints. Rationale: the labels are part of the model
  identity (they appear in reports), so a change in labels is a change
  in the model artefact.

### 7.2 Effect on existing models

Fingerprints computed **before 3.1** will not match fingerprints
computed **after 3.1** on the same data with the same hyperparameters.
The payload has changed.

**Acceptable.** At v1.0.0a1, no production models exist. The change is
documented in `audit_log.md` and the release notes of the next version.

**Migration path (documented, not implemented).** If a future version
needs to recognise fingerprints from both eras, a version byte can be
added to the payload. Not needed now.

## §10. Risks and mitigations

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| 1 | **Silent numerical change in K=2.** The multivariate Jeffreys reduces to the binary formula only if `K=2` and the priors are symmetric. | Low | High | Explicit test `test_multiclass_binary_parity` verifies the exact numbers match the pre-3.1 values. |
| 2 | **Consumer breaks due to `pd_final` becoming a tuple.** Every place that reads `pd_final` as a scalar must change to `pd_final[0]`. | Medium | High | Static review: grep for `.pd_final` in the entire repo; each occurrence is classified as scalar-read (adapt) or tuple-read (leave). |
| 3 | **Fingerprint change breaks existing cached fingerprints.** | Certain | Low | Documented. v1.0.0a1 is alpha; no production models. |
| 4 | **Wizard flow becomes longer.** Analyst must fill 2 new fields. | Certain | Low | Fields are in Step 2, alongside the existing target combo. UI layout has room. |
| 5 | **The minority-class warning is ignored.** The analyst sees the amber banner but proceeds. | Medium | Low | The choice is recorded in the log. If the analyst inverts by mistake, the post-training Gini badge (1quater.1) catches it. Two safety nets. |
| 6 | **Tests become brittle due to tuple assertions.** Assertions like `node.pd_final == 0.5` become `node.pd_final == (0.5,)` for K=2 with a single-element tuple... **NO**, for K=2 the tuple has 2 elements. Every tuple assertion is `== (a, b)`. | Medium | Low | Explicit note in each adapted test. |
| 7 | **The reversal button (1quater.3) does not preserve the partition.** The analyst's `train_frac` and `seed` are re-read from `SessionState`. | Low | Medium | The reversal reads the existing state, not a new wizard config. Test verifies idempotence. |
| 8 | **`Session.fix_spec` mandatory parameters break backward compatibility** with external scripts. | Certain | Low | Documented in `api.md`. v1.0.0a1 alpha; no external users yet. |

### 10.1 Non-negotiable invariants

These must hold at every commit of Phase 3.1:

- For K=2 with `target_class=1` and the standard labels, the model
  produced is **numerically identical** to the pre-3.1 model. Verified
  by `test_multiclass_binary_parity`.
- `sum(pd_final) == 1` for every node, for every K. Verified in
  `TreeModel.__post_init__`.
- `pd_final[0]` is always the probability of `target_class`. Verified
  in `TreeModel.__post_init__`.
- The full test suite passes: `python -m pytest tests -q` → all green.

## §11. Open questions

None at the time of this design. If a question arises during
implementation, it is recorded here and resolved before the
corresponding sub-phase is closed.

**Anticipated (not blocking):**

- **Naming of the label fields.** `class_labels` is chosen for
  symmetry with `target_class`. An alternative was `target_labels`. If
  a future need arises to distinguish "labels of the target classes"
  from "labels of any other categorical variable", the naming may be
  revisited.

- **Behaviour when `target_class` appears with extreme imbalance.**
  For a class with `k=0` in a leaf, `pd_jeffreys[0] = 0.5 / (n + K*0.5)`,
  a small but positive value. This is the intended Jeffreys behaviour.
  A future MRM concern might be "should the leaf PD be reported with
  its confidence interval?" — deferred, not in scope.

- **Metric threshold for the inversion badge.** Currently the badge
  triggers on `gini < 0`. A future refinement might trigger on
  `gini < 0.05` (near-zero discrimination). Not in scope for 3.1.
