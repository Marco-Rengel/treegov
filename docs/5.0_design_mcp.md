**Estado:** ✅ Implementado y cerrado (01/11/2026; suite 525/525).

**Predecesor:** Fase 4.0 — Exportadores de producción (cerrada 01/11/2026, suite 525/525).
**Inventario base:** las herramientas de este diseño se derivaron de

(`backend_v3/session_state.py`: propiedades y métodos públicos de

## §1. Contexto y objetivo

### 1.1 Qué es MCP

El *Model Context Protocol* es un estándar público y abierto que define cómo una
aplicación expone herramientas y datos a clientes de agentes LLM, con un esquema
formal completo. Sobre JSON-RPC 2.0, introduce tres primitivas: `tools`
(funciones invocables con esquema de entrada/salida), `resources` (datos
legibles por URI) y `prompts` (plantillas). Ofrece transportes de stdio local y
HTTP/SSE remoto. Es un estándar de interoperabilidad, como lo son BCBS o IFRS 9
para el dominio financiero: no es una librería de modelos.

### 1.2 Por qué TreeGov lo adopta

El flujo transaccional de TreeGov (cargar CSV → `fix_spec` → `partition` →
`train` → evaluar → exportar) ya vive completo en `backend_v3.Session`, sin
necesidad de la GUI. La Fase 4.0 llevó el modelo *hacia afuera* (exportadores
SQL/Python/Markdown); la Fase 5 lo expone *hacia el exterior* como servicio:
un agente LLM puede orquestar el flujo completo herramienta a herramienta,
comprobar resultados intermedios (gains table, matriz de clasificación,
semáforos PSI/CSI) y producir el artefacto final, bajo la misma máquina de
estados y la misma gobernanza que el analista usa en la GUI.

Dos señales del código ya prepararon este terreno:

- `docs/design_decisions.md` §18.7: el contrato de `Session.get_data_preview`
  es JSON-serializable nativo y "queda listo para serialización JSON en la
  futura capa MCP (Fase 5)".
- `Session.class_labels_dict` — docstring del backend: "conveniencia para
  GUI/MCP".

Perfil de uso objetivo: el analista de riesgo mantiene sus datos en su
máquina; un agente en su entorno local guía o automatiza la construcción del
modelo, el análisis de métricas y la generación de documentación, sin tocar
ninguna pantalla.

### 1.3 Qué NO incluye esta fase (delimitación)

| Fuera de alcance | Motivo |
|---|---|
| Reemplazar o modificar la GUI | Decisión registrada en `docs/roadmap.md` ("MCP as an adapter in Phase 5; it does not replace the GUI"). `frontend_v3/` queda intacto. |
| Transporte HTTP/SSE remoto multi-cliente | Confidencialidad perseguida con la decisión GUI (los datos bancarios no salen del escritorio). Solo stdio local. Multi-cliente diferido. |
| Scoring puntual/batch de filas nuevas | Interfaz de scoring es de la Fase 6 (batch scoring + champion-challenger). Esta fase no expone `predict_pd` como herramienta. |
| Lógica analítica nueva (fórmulas, tests estadísticos, defaults nuevos) | Sala limpia: toda la matemática ya está en `backend_v3` con cita bibliográfica. El adaptador no calcula nada. |
| Persistencia de la sesión entre reinicios del proceso | La GUI tampoco la tiene. Es de sesión, en memoria. |
| Declaración manual de tipos de predictor (spec crudo) | ZG-MCP-1, ver §2.4. |
| Export a ficheros desde el servidor | Los exportadores devuelven strings in-band; quien decide el destino final es el cliente del protocolo. |

**Lectura vs. escritura:** esta fase expone tanto operaciones de lectura como
las operaciones transaccionales ya públicas del flujo (`load_dataset`,
`fix_spec`, `train`, `evaluate_oos`, exportadores, `intervene_node`). El
principio limitante es otro: **el agente no gana ninguna capacidad que no
tenga hoy la GUI**. Toda herramienta mapea 1:1 a un método público
existente de `Session`; el adaptador añade cero funcionalidad analítica.

## §2. Alcance — inventario de herramientas

### 2.1 `tools` (canal principal, 24 herramientas)

Nombres en `snake_case`, espejo 1:1 de los métodos públicos de `Session`
(listados en `docs/api.md` §backend_v3.session_state). Estados según
`FlowState` (`EMPTY` → `DATA_LOADED` → `SPEC_FIXED` → `PARTITIONED` →
`TRAINED` → `OOT_LOADED` → `OOT_EVALUATED`). Los errores de estado los
emite `Session` y se propagan verbatim.

**Grupo A — Estado y lectura del dataset (los estados mínimos son por herramienta):**

| Tool | Método backend | Estado mínimo | Descripción |
|---|---|---|---|
| `get_session_state` | `Session.state` | EMPTY | Resumen del estado: FlowState, transacciones del event_log, fingerprint si existe. |
| `load_dataset` | `Session.load_dataset` | EMPTY | Carga un CSV local (ruta absoluta o relativa al proceso). |
| `describe_dataset` | `Session.describe_dataset` | DATA_LOADED | Perfil de columnas y tipos inferidos. |
| `get_data_preview` | `Session.get_data_preview` | DATA_LOADED | Vista cruda JSON nativa (contrato §18.7). |
| `describe_target` | `Session.describe_target` | DATA_LOADED | Distribución del target candidato. |
| `describe_weight_column` | `Session.describe_weight_column` | DATA_LOADED | Validez de un peso por muestra. |
| `describe_population_column` | `Session.describe_population_column` | DATA_LOADED | Validez del filtro de población. |

**Grupo B — Configuración del spec (transaccional):**

| Tool | Método backend | Estado mínimo | Descripción |
|---|---|---|---|
| `fix_spec` | `Session.fix_spec` | DATA_LOADED | Target + clase de interés + etiquetas por clase, subconjunto de predictores, `weight_col`, `population_col`, `cost_matrix`. Tipo de predictor inferido (`spec=None`); el spec crudo NO se expone (ZG-MCP-1). |
| `partition` | `Session.partition` | SPEC_FIXED | Holdout estratificado con `train_frac` y `seed`. |
| `reset_to_data_loaded` | `Session.reset_to_data_loaded` | ≥ DATA_LOADED | Vuelta atrás manteniendo el CSV en cache. |

**Grupo C — Entrenamiento y evaluación:**

| Tool | Método backend | Estado mínimo | Descripción |
|---|---|---|---|
| `train` | `Session.train` | PARTITIONED | Motor por nombre (`CHAID` / `CHAID_EXHAUSTIVE` / `CRT` / `QUEST`), `target_type`, `max_depth`, `min_child_size`, `min_child_weight`, modo gobernanza (D7). |
| `evaluate_oos` | `Session.evaluate_oos` | TRAINED | Métricas OOS multiclase (`n_groups`). |
| `get_oos_oot_report` | `Session.get_oos_oot_report` | TRAINED | DTO plano del informe OOS/OOT. |
| `get_gains_table` | `Session.get_gains_table` | TRAINED | Tabla de ganancias por hoja o por buckets. |
| `get_classification_matrix` | `Session.get_classification_matrix` | TRAINED | Matriz de confusión (binaria o K×K). |
| `get_univariate_trees` | `Session.get_univariate_trees` | TRAINED | Árboles univariados por predictor (mismo motor y gobernanza). |

**Grupo D — Interacción sobre el modelo entrenado:**

| Tool | Método backend | Estado mínimo | Descripción |
|---|---|---|---|
| `get_prune_sequence` | `Session.get_prune_sequence` | TRAINED | Secuencia coste-complejidad (α, n_leaves, r_subtree). |
| `prune` | `Session.prune` | TRAINED | Aplica la poda coste-complejidad con el α indicado. |
| `intervene_node` | `Session.intervene_node` | TRAINED | Intervención manual (acción `prune_branch`); salida eco del Manual Override Log (D9). |

**Grupo E — OOT (monitoreo de estabilidad):**

| Tool | Método backend | Estado mínimo | Descripción |
|---|---|---|---|
| `load_oot` | `Session.load_oot` | TRAINED | Cohorte temporal posterior (con `time_col`). |
| `evaluate_oot` | `Session.evaluate_oot` | OOT_LOADED | Métricas OOT + PSI/CSI + Gini Drop. |

**Grupo F — Export (artefactos in-band):**

| Tool | Método backend | Estado mínimo | Descripción |
|---|---|---|---|
| `export_sql` | `Session.export_to_sql` | TRAINED | SQL ANSI `CASE WHEN` + `COALESCE`, fingerprint en cabecera. |
| `export_python` | `Session.export_to_python` | TRAINED | Módulo Python sin dependencias. |
| `export_markdown` | `Session.export_to_markdown` | TRAINED | Informe legible en Markdown. |

### 2.2 Tipado de esquemas de entrada

Los esquemas usan tipos JSON estándar (`string`, `number`, `integer`,
`boolean`, `array`, `object`). Los valores de enumeración que ya existen en
el backend se propagan como enums en el esquema (motor, `target_type`,
modo gobernanza). `class_labels` y `cost_matrix` viajan como `object`/`array`
y se validan con la validación rigurosa que `Session.fix_spec` ya hace hoy.

### 2.3 `resources` y `prompts` (primitivas MCP adicionales)

Fuera del alcance de esta fase. 24 herramientas cubren el flujo completo; las
primitivas adicionales añaden superficie de protocolo sin caso de uso
inmediato. Se difiere explícitamente a una sub-fase posterior (5.1 o fase
futura); el veredicto A6 del §4 lo registra como decisión, no como deuda.

### 2.4 Zonas grises gestionadas (opción conservadora)

- **ZG-MCP-1 — spec crudo.** `fix_spec` acepta `spec: dict[str, PredictorType]`
  para declarar tipos a mano (path de experto). El esquema de la herramienta
  no lo expone: se conserva la inferencia (`spec=None`, `profiling.infer_spec`),
  que es la misma semántica default de la GUI. Forzar tipos por MCP queda
  diferido y documentado; no es deuda técnica, es una restricción deliberada
  del alcance para impedir que el agente declare enums crudos arbitrarios.
  `TODO(zona_gris)` marcado en el descriptor de la herramienta al implementar.
- **ZG-MCP-2 — errores.** No se traducen, no se parafriscean: el texto del
  backend (`ValueError`/`RuntimeError`/`FileNotFoundError`) viaja verbatim al
  cliente. La paráfrasis rompería la trazabilidad establecida por los tests
  y el audit_log existentes.

## §3. Decisiones de arquitectura

| ID | Decisión | Justificación |
|---|---|---|
| **D1** | Nueva capa `mcp_v3/` (tercera respecto a `backend_v3/` y `frontend_v3/`). | El adaptador de protocolo es un asunto de presentación comparable a `frontend_v3`; no comparte dependencias con ninguna de las dos capas. `backend_v3/` no se toca (ni Qt ni dependencias nuevas) y `mcp_v3/` no importa Qt/PySide6 ni implementa fórmulas. |
| **D2** | Registro de herramientas como dato plano, no código de servidor. | `mcp_v3/tools.py` es una lista de descriptores `frozen` (nombre, esquema, estado mínimo, handler, docstring) independiente del SDK MCP. Todo se testea headless sin SDK; el servidor (5.0.b) solo ensambla protocolo. |
| **D3** | SDK de MCP como dependencia opcional (`[project.optional-dependencies] mcp = [...]`). | El núcleo PyPI (`treegov`) no crece para los usuarios GUI existentes; el extra `mcp` lo activa quien lo necesite. Import lazy con mensaje de instalación claro. El protocolo es un estándar público, no lógica analítica: no viola la sala limpia —§0.5 de `design_decisions.md`—, cuya prohibición rige la lógica analítica y la refuerza `import_guard`. |
| **D4** | Exactamente una `Session` por proceso de servidor; ciclo de vida del protocolo == ciclo de la `Session`. | El transporte de 5.0 es de stdio (un cliente por proceso), lo que hace natural el mapeo directo. Al reiniciar el cliente, la Session se reconstruye (D10). Sin estado global para múltiples sesiones. |
| **D5** | Transporte stdio local único en esta fase. | Continúa la propiedad del dato que no sale del escritorio, que motivó elegir la GUI PySide6 en vez de una webapp (`docs/roadmap.md`, decisión GUI). El transporte HTTP/SSE multi-cliente se reevaluará en una fase futura con requisitos de despliegue concretos. |
| **D6** | Contrato de salida: DTOs planos JSON nativos con punto único de conversión (`mcp_v3/dto.py::_jsonable`). | `json.dumps(salida, allow_nan=False)` no debe fallar para ninguna herramienta (invariante I-3). Escalares de numpy/pandas → nativos; `NaN`/`Inf` → `None`; dataclasses `frozen` → `dict` (asdict). Es la prolongación directa del contrato ya fijado en `get_data_preview` (§18.7). |
| **D7** | `train` expone solo modo gobernanza canónico (`"banking"` / `"research"`), traducido con la correspondencia exacta del backend: research → `pd_floor=None` + `apply_jeffreys=False`; banking → defaults del backend (`pd_floor=0.0005`, `apply_jeffreys=True`). | Impide combinaciones ambiguas (p. ej. floor sin Jeffreys) que mezclarían la semántica de ambos modos. La correspondencia se fija en un test de paridad contra los valores canónicos (`docs/api.md` y el wizard); el `params_fingerprint` del modelo entrenado sigue siendo la única verdad del modo (I-2). |
| **D8** | Registro de eventos exclusivamente en stderr; mismo `log_config.get_logger`; sin prints, sin telemetría. | En stdio, stdout es el canal del protocolo: cualquier byte extra inutiliza la sesión. El DEBUG transaccional por run (`log_config`) es requisito del auditor MRM — se mantiene intacto y persiste solo en el fichero de registro local. |
| **D9** | Las acciones que en la GUI piden confirmación (`intervene_node` en modo BANKING) NO replican diálogo sintético en el servidor. | El consentimiento es asunto del cliente del protocolo. El servidor expone la consecuencia: salida eco del Manual Override Log con `fp_before` → `fp_after` (comportamiento previo ya documentado en Fase 3.11.d). |
| **D10** | Cero persistencia entre reinicios: la `Session` muere con el proceso. | Igual que la GUI. El CSV es la única fuente de datos en disco; el Override Log se construye en memoria por sesión, como hoy. No hay storage adicional, no ficheros de estado nuevos. |
| **D11** | Acceso a ficheros: solo explícito por ruta en `load_dataset`/`load_oot`; sin herramientas de browsing ni glob. | El backend ya valida rutas (`FileNotFoundError`). El sandboxing de rutas se evaluará en la auditoría de seguridad (5.0.d); si se detecta riesgo, se restringirá con una whitelist configurable y se documentará como decisión, no como parche. |

## §4. Alternativas consideradas y descartadas

| ID | Alternativa | Veredicto | Motivo |
|---|---|---|---|
| A1 | REST/HTTP con FastAPI y OpenAPI | Descartada | Duplicaría el despliegue (servidor HTTP, auth, TLS) para el mismo objetivo; los clientes del ecosistema de agentes hablan el protocolo MCP, no REST ad-hoc. Además, la exposición HTTP remota choca con la confidencialidad de §1.3. Esta ruta se reevaluará si aparece un requisito de integración servidor-a-servidor. |
| A2 | Protocolo JSON-lines propio sobre stdin/stdout sin SDK | Descartada | Reinventa un estándar público sin necesidad y pierde el ecosistema de clientes. Un protocolo propio también necesitaría su propia suite de conformidad; el coste supera a D3 (dependencia opcional, registro desacoplado). |
| A3 | Exponer los motores directamente (sin `Session`) | Descartada | La `Session` garantiza máquina de estados, atomicidad, cache del `TrainOnlyImputer` y gobernanza. Omitirlo re-expone el leakage de imputación y borra el fingerprint como contrato. Duplicaría gobernanza en el adaptador (violación de I-2). |
| A4 | Reconstruir el wizard como driver headless de Qt | Descartada | El wizard es presentación; `Session` es el orquestador transaccional que la GUI ya consume. Automatizar Qt offscreen para orquestarlo no es estable y mezclaría UI con lógica transaccional. |
| A5 | Webapp (p. ej. Streamlit/docker) como capa de agentes | Descartada | Ya descartada en las decisiones de roadmap por confidencialidad (los datos no salen del escritorio) y por acoplamiento de capa de agentes a un despliegue web. |
| A6 | Exponer `resources`/`prompts` además de `tools` desde el día 1 | Diferida | Sin caso de uso inmediato; añaden superficie de protocolo a auditar. Se reevalúan tras el primer uso real de las 24 tools. |
| A7 | Exponer `predict_pd` per-row para "probar el modelo" desde el agente | Diferida a Fase 6 | La Fase 6 (batch scoring + champion-challenger) es la dueña de la interfaz de scoring; duplicarla aquí crearía dos contratos en competencia. |

## §5. Invariantes

- **I-1. Sala limpia.** `mcp_v3/` no importa `PySide6`/Qt ni nada de
  `frontend_v3/`; no implementa fórmulas ni estadística (sin nuevos cálculos,
  ni siquiera de conveniencia). `backend_v3/` no cambia ni gana dependencias.
  Los bloqueos del `import_guard` (sklearn, statsmodels, xgboost, lightgbm,
  catboost) permanecen vigentes en las tres capas.
- **I-2. Gobernanza nativa.** Ninguna herramienta reinterpreta el modo
  regulatorio; el `params_fingerprint` sigue siendo la única verdad del modo
  (BANKING/RESEARCH). Jeffreys + PD Floor (BCBS CRE 32.4) intactos como
  defaults del backend. La correspondencia mode→params es única y testeada
  (D7).
- **I-3. DTO JSON-serializable.** Para la salida de TODAS las herramientas:
  `json.dumps(payload, allow_nan=False)` nunca lanza. Escalares numpy/pandas
  → nativos; NaN/Inf → `None`; dataclasses → dict (D6).
- **I-4. Mapeo 1:1, sin lógica nueva.** Cada descriptor de herramienta
  referencia exactamente un método público de `Session`; ningún handler
  contiene ifs de negocio. Si una necesidad revela que falta un método
  público, se escala como decisión documentada, nunca se parchea en el
  adaptador.
- **I-5. Errores verbatim.** Los mensajes de `Session`/backend atraviesan el
  adaptador sin moderar (ZG-MCP-2); el estado requerido por herramienta figura
  en su descriptor para diagnóstico.
- **I-6. Determinismo y paridad con la GUI.** Una misma secuencia de llamadas
  por MCP produce los mismos DTOs y el mismo fingerprint que la misma
  secuencia en la GUI. Paridad verificada por tests E2E headless (5.0.c).
- **I-7. Confidencialidad.** Solo transporte stdio local en esta fase;
  sin telemetría; ficheros de registro locales vía `log_config`; el protocolo
  no persiste el dataset en ninguna ruta adicional.
- **I-8. Fingerprint intacto.** El adaptador no calcula ni manipula el
  fingerprint; los exports conservan el fingerprint como cabecera de
  comentario (comportamiento ya existente en `exporters.py`, Fase 4.0).

## §7. Riesgos y mitigaciones

| ID | Riesgo | Impacto | Mitigación |
|---|---|---|---|
| R1 | El estándar MCP evoluciona rápido (la spec y el SDK avanzan con cambios de rompimiento frecuentes). | Media | Dependencia opcional con versión fijada (D3); el adaptador es cola delgada (D2) para que un salto de versión toque un solo archivo (`server.py`). |
| R2 | Escalares numpy/pandas (especialmente `NaN`) llegan al JSON-RPC como tipos no válidos. | Alta | Invariante I-3 codificado como test parametrizado sobre las 24 herramientas desde 5.0.a; punto único de conversión (D6). |
| R3 | Bytes extra-protocolo en stdout (logging o librerías) corruptan el canal stdio. | Alta | D8: todo registro a stderr; sin `print`; test de humo que captura el stdout del arranque del servidor y verifica ausencia de contaminación. |
| R4 | Deriva de gobernanza: el mapeo mode→params del servidor diverge del de la GUI. | Alta | D7: correspondencia única fijada por test de paridad contra los valores canónicos (`docs/api.md`, wizard); el fingerprint en la salida permite contrastar la paridad directamente en la suite (misma estrategia que los fingerprints UCI de la Fase 3.8.d). |
| R5 | El agente llama herramientas fuera de orden (estado transaccional). | Baja | La `Session` ya garantiza el orden transaccional con `ValueError` claros; el descriptor llevará el estado mínimo requerido; el error verbatim educa al agente (I-5). |
| R6 | Superficie de datos: `load_dataset` con ruta arbitraria en el proceso local. | Media | D11 + 5.0.d: revisión de seguridad con apéndice en `docs/security_audit.md`; sandbox/whitelist solo si aparece amenaza concreta. |
| R7 | Rendimiento del preview/gains en datasets grandes sobre el canal JSON. | Baja | `get_data_preview` ya está acotado (default 50 filas, `truncated`); las tablas de ganancias tienen N buckets acotado. Métricas de benchmark posteriores solo si un caso real lo exige. |
| R8 | Doble configuración de logging (servidor MCP vs log_config del backend). | Baja | Un solo mecanismo: `get_logger`/`setup_logging` de `log_config`, redirigido a stderr en `server.py` (D8). Sin configuración nueva. |
