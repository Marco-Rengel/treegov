# TreeGov — Phase 3.6 design: validation with public datasets

**Purpose.** This document defines the design of Phase 3.6 (validation of
the TreeGov pipeline against well-known public datasets) before any code
is written. It is the reference for the implementation sub-phases 3.6.a
to 3.6.d, and the audit trail for the design decisions D1 to D9,
approved by the author on 16/10/2026 as a single block.

**Audience.** The project author, future maintainers, and any MRM
reviewer who needs to understand how TreeGov is validated against
datasets that a third party can independently obtain, and why those
particular datasets were chosen.

**Status.** Approved by the author on 16/10/2026. The nine design
decisions (D1–D9) were reviewed and approved as a block. No code has
been written yet; this document precedes implementation, per the
project's methodological rule (design, audit the design, then
implement).

**Companion documents.**
- `docs/3.1_design_multiclass.md` — Phase 3.1 design (multiclass tree layer).
- `docs/3.2_decisions_consolidated.md` — Phase 3.2 decisions (sample weighting).
- `docs/3.3_design_population_categories.md` — Phase 3.3 design (population categories).
- `docs/3.4_design_multiclass_crt_quest.md` — Phase 3.4 design (multiclass C&RT and QUEST).
- `docs/3.5_design_multiclass_weighted_reports.md` — Phase 3.5 design (multiclass and weighted reports). This document mirrors its structure.
- `docs/design_decisions.md` — implementation decisions across the project.
- `docs/methodology.md` — mathematical formulas with citations.
- `docs/roadmap.md` — phase plan; Phase 3.6 entry.
- `docs/audit_log.md` — chronological log; entries of 13/10/2026 (GUI session, first mention of Phase 3.6 needs).

## §0. Scope and objective

### 0.1 What 3.6 delivers

Phase 3.6 validates the TreeGov pipeline — engines, tree builder,
metrics, reports, and stability — against publicly available datasets
whose statistical properties are known to a third party and whose
values can be independently reproduced. The phase does not add new
functionality to the analytical core.

Concretely, 3.6 delivers:

- **A reproducible data acquisition script.** `scripts/fetch_datasets.py`
  downloads three public datasets from UCI, verifies their SHA256
  hashes, and normalises them to a TreeGov-ready CSV format. Any user
  with an internet connection can regenerate the CSVs bit-for-bit from
  the canonical UCI sources.
- **Versioned dataset fixtures.** The normalised CSVs of the three
  datasets (German Credit, Car Evaluation, Balance Scale) are
  versioned inside `tests/fixtures/uci/` and become part of the
  repository. They are the ground truth for the integration tests.
- **Integration tests.** `tests/test_uci_integration.py` runs the full
  TreeGov pipeline (load, fix_spec, partition, train, evaluate_oos,
  report) on each of the three datasets with a fixed seed and verifies
  the resulting fingerprint, tree structure, and metric ranges against
  values hand-computed during 3.6.c.
- **A validation report.** `docs/validation_results_3.6.md` records the
  metrics obtained on each dataset (fingerprint, Gini, KS, AUC,
  accuracy, number of leaves) as a reproducible baseline. The report
  also situates each result qualitatively against the ranges published
  in the credit-scoring literature, without claiming exact agreement
  with any specific paper.

### 0.2 What 3.6 does NOT deliver

- **New functionality.** No new engines, no new metrics, no changes to
  `backend_v3/`. If a bug is found during validation, it is recorded
  in `docs/audit_log.md` and deferred to a separate corrective
  sub-phase; 3.6 does not become a debugging vehicle.
- **Continuous regression metrics.** Only classification targets are
  validated (binary and multiclass). Regression (`TargetType.CONTINUOUS`)
  remains blocked at the builder level since Phase 3.1 and is out of
  scope, consistent with `docs/3.5_design_multiclass_weighted_reports.md`
  §0.2.
- **Cost-sensitive learning.** The asymmetric cost matrix shipped with
  German Credit is deliberately ignored. Decision D5 makes this
  explicit; the mathematical and operational reasons are in §3.6 below.
- **Feature engineering.** Datasets are fed to TreeGov with the
  columns as UCI publishes them, modulo the encoding and column-naming
  normalisation of §3. No derived features, no scaling, no selection.
  The point is to validate the engine on raw, well-known data.
- **Cross-validation.** TreeGov does not implement k-fold CV today
  (deferred to Phase 2.1.b per `docs/roadmap.md`, "Deferred" section).
  Phase 3.6 uses a single fixed train/test split with a documented
  seed, consistent with every other validation in the project since
  Phase 1.2.
- **Performance benchmarking.** Throughput and memory are already
  measured by `tests/benchmark_1m.py`. Phase 3.6 measures correctness
  and reproducibility, not speed.

### 0.3 Why this scope

Two arguments justify validating against public datasets before
proceeding to Phase 3.7 (v1.0.0 stable).

**First, internal consistency is not external validity.** Every metric
implemented in TreeGov today has been tested against hand-computed
values (see `docs/methodology.md` §8.1–§8.14 and the audit-log entries
of Phases 1.2, 1.3, 3.2, 3.5). That is necessary and, so far,
sufficient. It is not the same as showing that the pipeline produces
sensible results on data whose statistical structure is independently
documented. A regression in the tree builder that happens to preserve
every hand-computed fixture value but degrades Gini on real data would
pass today's 416/416 suite. Phase 3.6 closes that gap.

**Second, reproducibility is a first-class MRM property.** An MRM
reviewer auditing TreeGov must be able to re-run the validation and
obtain the same numbers. If the datasets were only referenced by URL,
the reviewer would depend on UCI's availability and on the exact
version of the files at the time of the audit. Versioning the
normalised CSVs as repository fixtures makes the validation
self-contained: `git clone` + `pytest tests/test_uci_integration.py`
reproduces the baseline bit-for-bit.

The scope is deliberately minimal — three datasets, one split, one
report — so that the validation is cheap to re-run and easy to
understand. Extending the set (Adult / Census, Tic-Tac-Toe, Wine,
Iris) is deferred to a later phase if a need arises.

## §1. Current state

### 1.1 The pipeline at the end of Phase 3.5

At the close of Phase 3.5 (15/10/2026), TreeGov can:

- Load a CSV via `Session.load_dataset` (`backend_v3/session_state.py`).
- Infer predictor types via `profiling.infer_spec` (nominal, ordinal,
  continuous) with the `MAX_ORDINAL_CATS=20` heuristic.
- Fix the spec, target class, class labels, weight column, and
  population column via `Session.fix_spec`.
- Partition train/test with exact Hamilton-Hare stratification.
- Train a tree with CHAID, CHAID_EXHAUSTIVE, C&RT, or QUEST (all four
  support K ≥ 2 since Phase 3.4).
- Evaluate OOS and OOT with the multiclass-general metrics of Phase 3.5.
- Produce gains table and classification matrix DTOs for any partition.
- Monitor stability (PSI, CSI, Gini Drop).

Every step is exercised by the 416/416 suite. The suite runs on
**synthetic fixtures** (`_make_csv`, `_make_csv_population`, and
similar helpers in `tests/test_e2e_*.py`) and on hand-computed unit
fixtures with values verified against textbook formulas.

### 1.2 Why synthetic data is not enough

The synthetic fixtures serve two purposes: exercising the plumbing
(load, partition, train, evaluate, refresh panels) and pinning down
specific numerical values for unit tests. They are excellent at the
first, adequate at the second, and structurally incapable of doing
what Phase 3.6 needs.

The reason is recorded explicitly in `docs/roadmap.md`, "Deferred"
section, entry "E2E test fixture: target con señal real":

> El helper `_make_csv` de `tests/test_e2e_mainwindow.py` y
> `tests/test_e2e_reports.py` genera un target con relación aleatoria a
> los predictores, por lo que el Gini OOS es ruido de pequeña magnitud.
> Esto hace que los tests E2E verifiquen el plumbing (flujo, refresco,
> señales, transiciones) pero no la analítica real.

The consequence is concrete: a model trained on `_make_csv` produces
near-zero Gini regardless of whether the tree builder is correct. The
sign of that near-zero Gini depends on random fluctuation (this is
also documented in the audit-log entry of 16/10/2026 for Phase 3.1.f,
where the `target_class=1` fixture happens to give a slightly negative
Gini). A regression that inverted the sign of the Gini — the sort of
bug that would invalidate every credit-scoring model in production —
would not be detected by the current suite.

### 1.3 What's already verified

Before Phase 3.6, the following have been verified by the existing
suite and do not need re-verification here:

- Every statistical formula, against hand-computed values with
  bibliographic citations (see `docs/methodology.md` §1 through §8).
- Every engine's split decisions, against hand-computed fixtures.
- Binary parity K = 2 (bit-for-bit against pre-3.1 and pre-3.5) —
  the central invariant of Phases 3.1 and 3.5.
- Fingerprint determinism, tree reindexing after pruning, and Session
  state transitions.

What Phase 3.6 adds is not another layer of the same kind of test. It
adds a new *category*: end-to-end validation on externally documented
data, with reproducible fingerprints, on targets the literature knows.

## §2. Dataset selection (D1)

Three datasets are used, one per axis of the pipeline. The choice is
minimal by design: enough to exercise the three-dimensional space
(binary vs multiclass × categorical vs numeric × balanced vs imbalanced),
no more.

### 2.1 German Credit (Statlog)

**Source.** UCI Machine Learning Repository, dataset 144
(Statlog / German Credit Data).

**Shape.** 1000 rows. 20 predictors (7 numeric, 13 categorical as
published in `german.data`). Binary target (Good / Bad).

**Why this dataset.** It is the canonical credit-scoring dataset in the
academic literature. Any reviewer of TreeGov with a credit-risk
background will recognize it immediately, which is precisely the
audience for whom Phase 3.6 exists. Its event rate (300 Bad / 1000
total = 30%) is realistic for retail credit. Its mix of numeric and
categorical features exercises both threshold-based and
category-merging splits in the same run.

**What 3.6 uses it for.** Binary validation of the full pipeline
(CHAID, C&RT, QUEST on the same dataset with a fixed seed). The point
is not to find the "best" model but to show that all four engines
produce stable, reproducible, and mutually consistent results.

**What 3.6 does not use it for.** The 5×5 asymmetric cost matrix
published in `german.doc` is ignored — see D5 and §3.6 below.

### 2.2 Car Evaluation

**Source.** UCI Machine Learning Repository, dataset 19 (Car Evaluation).

**Shape.** 1728 rows. 6 categorical predictors (all string-valued, all
nominal: `buying`, `maint`, `doors`, `persons`, `lug_boot`, `safety`).
Multiclass target with K = 4 (`unacc`, `acc`, `good`, `vgood`).

**Why this dataset.** It is the natural complement to German Credit:
purely categorical (no thresholds involved), purely nominal (no
ordinality), and severely imbalanced (1210 / 384 / 69 / 65 = 70% / 22%
/ 4% / 4%). This exercises the multiclass machinery delivered in
Phases 3.1, 3.4, and 3.5 under conditions where one class dominates and
two are rare. Specifically:

- CHAID's iterative merging with K = 4 classes.
- C&RT's multiclass Gini impurity (§2.1 of `docs/methodology.md`).
- QUEST's Stage 2 Gini sweep for K > 2 (§3.8 of `docs/methodology.md`).
- The multiclass reports (gains table, K×K matrix) of Phase 3.5.

**What 3.6 uses it for.** Multiclass validation on categorical-only
data, with a class imbalance that stresses the K×K confusion matrix
and the worst-case pairwise KS.

### 2.3 Balance Scale

**Source.** UCI Machine Learning Repository, dataset 12 (Balance Scale).

**Shape.** 625 rows. 4 ordinal predictors (`left_weight`,
`left_distance`, `right_weight`, `right_distance`, each in {1, 2, 3, 4,
5}). Multiclass target with K = 3 (`L`, `B`, `R`).

**Why this dataset.** It complements the other two along the
predictor-type axis: all features are ordinal. The
`MAX_ORDINAL_CATS=20` heuristic will classify each of them as ORDINAL,
which is semantically correct (`left_weight=5` is meaningfully greater
than `left_weight=1`). This exercises:

- CHAID's ORDINAL fusion rule (only adjacent categories merge) —
  distinct from the NOMINAL path used by Car Evaluation.
- QUEST's continuity assumption on ordinal features (QDA cutpoint for
  K = 2, Gini sweep for K > 2).
- C&RT's threshold search on values with heavy ties (5 distinct values
  per feature).

Its class distribution is also informative: 288 L / 288 B / 49 R. Two
classes balance, one is rare (7.8%). This is not as extreme as Car
Evaluation's `vgood` (3.8%) but it stresses a different aspect: K = 3
(the boundary case for Hand & Till AUC being non-trivial) with an
ordinal feature space.

**What 3.6 uses it for.** Multiclass validation on ordinal-only data,
with K = 3 (the smallest nontrivial multiclass) and 5-value
ordinality.

### 2.4 What 3.6 does NOT validate

Datasets considered and deliberately excluded:

- **Adult / Census Income.** 48k rows, mixed numeric and nominal,
  binary. Would be a good "large dataset" validation, but its size
  (~4 MB raw) and its pre-processing quirks (the "?" missing-value
  marker, several features with high cardinality) would drag 3.6 into
  data-cleaning decisions that belong in a separate phase. Deferred.
- **Iris.** 150 rows, 4 numeric features, 3 balanced classes. Too
  small and too easy to be informative; the tree never grows deep
  enough to test the tree builder meaningfully.
- **Wine.** 178 rows, 13 numeric features, 3 balanced classes. Similar
  to Balance Scale in spirit but with numeric instead of ordinal
  features; Balance Scale is preferred because it tests ordinality,
  which no other selected dataset does.
- **Tic-Tac-Toe Endgame.** 958 rows, 9 nominal features, binary target.
  Structurally similar to Car Evaluation (categorical-only, binary).
  Redundant given Car Evaluation's presence.

The three selected datasets cover the design space along the three
axes that matter for the pipeline. Adding a fourth would not add a new
axis.

## §3. Normalisation protocol (D3, D9)

The fetch script produces CSVs that `Session.load_dataset` can read
directly. No change to `backend_v3/` is required; the protocol below
defines the contract between the external dataset and the internal
loader.

### 3.1 Contract of a "TreeGov-ready" CSV

A CSV is TreeGov-ready when:

1. It has a header row with one column per field, using lowercase
   snake_case names with ASCII characters only.
2. The target column is named `target` unless the original dataset has
   an obvious English name that is clearer (see §3.4 for German
   Credit, which uses `creditability`).
3. All predictor columns are either numeric (int or float) or string.
   No datetime, no boolean, no categorical pandas dtype.
4. The target column is integer-coded 0..K-1, contiguous, in the
   order published by the source (or, for German Credit, in the order
   documented in §3.2).
5. No column contains NaN. (None of the three selected datasets has
   missing values in its canonical published form.)
6. Column order in the CSV does not matter for TreeGov — `fix_spec`
   determines the predictor list explicitly — but the fetch script
   writes the target as the last column for readability.

### 3.2 German Credit normalisation

The source file `german.data` (space-separated, no header) has 21
columns: 20 predictors + 1 target. The target is published as
`1 = Good`, `2 = Bad`. The fetch script:

- Renames each column with a descriptive snake_case name drawn from
  the attribute table of `german.doc` (e.g. `checking_status`,
  `duration_months`, `credit_history`, `purpose`, `credit_amount`,
  `savings_status`, `employment`, `installment_rate`, `personal_status`,
  `other_parties`, `residence_since`, `property_magnitude`, `age`,
  `other_payment_plans`, `housing`, `existing_credits`, `job`,
  `num_dependents`, `own_telephone`, `foreign_worker`).
- Preserves the original UCI codes for categorical features (`A11`,
  `A12`, ..., `A201`, `A202`) — see D9 and §3.5.
- Rewrites the target as `creditability` with `Bad → 1`, `Good → 0`.
  Rationale: TreeGov's event coding convention is `1 = event of
  interest`. For credit scoring, the "event" is default (Bad). A model
  trained with `target_class=1` will therefore compute PD as
  `P(Bad)` with the canonical reordering of Phase 3.1.

The result is `data/uci/german_credit/german_credit.csv`: 1000 rows,
21 columns, no missing values, target `creditability` ∈ {0, 1}.

### 3.3 Car Evaluation normalisation

The source file `car.data` (comma-separated, no header) has 7 columns:
6 predictors + 1 target. The target is published as
`unacc / acc / good / vgood`. The fetch script:

- Names the columns `buying`, `maint`, `doors`, `persons`, `lug_boot`,
  `safety`, `target`.
- Leaves all predictor values as published strings (`vhigh`, `high`,
  `med`, `low` for buying/maint; `2`, `3`, `4`, `5more` for doors;
  `2`, `4`, `more` for persons; `small`, `med`, `big` for lug_boot;
  `low`, `med`, `high` for safety).
- Rewrites the target as integers `unacc → 0`, `acc → 1`, `good → 2`,
  `vgood → 3`. The order preserves the semantic ordering of the
  original (worse to better) and matches the class counts published by
  UCI: 1210 / 384 / 69 / 65.

The result is `data/uci/car_evaluation/car_evaluation.csv`: 1728 rows,
7 columns, no missing values, target ∈ {0, 1, 2, 3}.

### 3.4 Balance Scale normalisation

The source file `balance-scale.data` (comma-separated, no header) has
5 columns: 4 predictors + 1 target. The predictors are integers in
{1, 2, 3, 4, 5}. The target is published as `L`, `B`, `R`. The fetch
script:

- Names the columns `left_weight`, `left_distance`, `right_weight`,
  `right_distance`, `target`.
- Leaves the predictors as published integers.
- Rewrites the target as integers `L → 0`, `B → 1`, `R → 2`. The order
  is arbitrary but fixed; the counts are 288 / 288 / 49.

The result is `data/uci/balance_scale/balance_scale.csv`: 625 rows,
5 columns, no missing values, target ∈ {0, 1, 2}.

### 3.5 Preserve original UCI codes (D9)

For German Credit, the categorical features retain their original
`A11`, `A12`, ... codes rather than being translated to human-readable
strings. The decision has three parts.

**Why not translate.** Translating `A11 → "checking_status_negative"`
would require a curated mapping. That mapping is a judgment call
about the semantics of each code, and different published descriptions
of the dataset disagree on nuances (for example, whether `A11` means
"no checking account" or "negative balance"). Introducing such a
mapping into the fixture would put a non-UCI decision into what is
supposed to be a UCI-faithful reproduction.

**Why the codes are not a problem for TreeGov.** The engines treat
nominal features as opaque hashable labels. `A11` and `A12` are just
two categories, no different from `foo` and `bar`. Preserving the
codes does not affect any numerical result; it only affects
readability.

**How the report compensates.** `docs/validation_results_3.6.md` will
include a short appendix table mapping the codes to their published
descriptions, sourced directly from `german.doc`. This keeps the
fixtures faithful and the report readable, without contaminating the
data.

## §4. Fetch script (D2)

### 4.1 Purpose and location

`scripts/fetch_datasets.py` downloads the three original UCI files,
verifies their SHA256 hashes, normalises them per §3, and writes the
resulting CSVs into `data/uci/<dataset>/`. It is the *only* way the
repository produces the normalised CSVs, and it is idempotent.

The script lives under `scripts/`, a new directory. There is no
`scripts/` directory in the repository today (checked on 16/10/2026);
creating it is part of 3.6.b.

### 4.2 Hash verification

The script contains a hardcoded dictionary of expected SHA256 hashes,
one per source file. After downloading each file, the script computes
its SHA256 and compares. On mismatch it raises `RuntimeError` with both
the expected and the actual hash, and does not write the normalised
CSV.

**Where the hashes come from.** The hashes are captured *at the moment
of the first verified download* during 3.6.b, by the author, using a
fresh connection to UCI. This document does not presuppose specific
hash values; it only records the protocol. The hashes hardcoded in the
final script are the authoritative ones, and any future mismatch
triggers a manual review.

**Why hashes matter.** Two failure modes motivate them:

1. **Silent dataset change.** UCI occasionally republishes files with
   minor corrections. If TreeGov's fixtures silently absorb such a
   change, the fingerprints in `docs/validation_results_3.6.md` would
   become unreproducible without anyone noticing.
2. **Transport corruption.** Rare, but not impossible over HTTPS. A
   silent corrupted download would produce a normalised CSV that
   produces a different fingerprint, again breaking reproducibility.

The script uses only the Python standard library (`urllib.request` for
the download, `hashlib` for SHA256, `zipfile` for the two datasets
that UCI distributes as ZIP archives in its modern interface). No new
dependency enters `pyproject.toml`.

### 4.3 Idempotence and re-download

The script behaves as follows:

- If `data/uci/<dataset>/<dataset>.csv` exists and its SHA256 matches
  a *derived* hash stored in a sidecar `.sha256` file, the script
  skips the download and exits with status 0.
- If the CSV does not exist, the script downloads the source files,
  verifies the source hashes, normalises, writes the CSV, and writes
  the derived `.sha256` sidecar.
- If the CSV exists but its hash does not match the sidecar, the
  script refuses to overwrite it and raises `RuntimeError`, asking
  the user to inspect the discrepancy manually. This is intentional:
  TreeGov does not overwrite artefacts without a human decision.

`data/uci/` remains under the `data/*` gitignore rule (see §5.1), so
the script's output is never committed. The versioned artefacts are
the fixtures under `tests/fixtures/uci/`.

## §5. Test strategy (D4, D6)

### 5.1 Versioned fixtures vs downloaded data

The integration tests do **not** depend on `data/uci/` being populated.
They read from `tests/fixtures/uci/`, a directory that is versioned in
the repository and contains the same normalised CSVs as the fetch
script produces.

This resolves the tension between two requirements:

- **Reproducibility.** A reviewer who clones the repo and runs
  `pytest` must obtain the same results as the author, without
  requiring internet access or a fresh download from a third party.
  This is satisfied by the versioned fixtures.
- **Faithfulness to the source.** The fixtures must be identical to
  what the fetch script produces from UCI's published files.
  This is satisfied by the derived `.sha256` sidecar comparison:
  running the fetch script and comparing the outputs against the
  fixtures is a two-line check documented in `docs/validation_results_3.6.md`.

The `.gitignore` rule for `data/*` is not extended to
`tests/fixtures/`; the latter is intentionally tracked. The fixtures
total roughly 150 KB (German Credit ≈ 80 KB, Car Evaluation ≈ 30 KB,
Balance Scale ≈ 20 KB), which is well within any reasonable repository
size budget.

**Why not a frozen subset.** An alternative considered was to version
a small subset of each dataset (for example, 100 rows of German
Credit) and skip the full test if the full dataset were not
downloaded. Rejected for two reasons: (a) a 100-row subset has
different statistical properties from the full dataset, so the Gini
and the tree structure would differ from what the literature
documents; the fingerprint would be a fixture-specific value, not a
baseline against the real dataset. (b) A conditional skip silently
weakens the test suite on machines without the full dataset, which is
exactly the failure mode this phase exists to prevent.

### 5.2 What each test verifies

`tests/test_uci_integration.py` contains, for each dataset:

1. **Load test.** `Session.load_dataset` on the fixture succeeds and
   reports the expected `n_rows` and `n_cols`.
2. **Spec test.** `fix_spec` with the documented target class and
   class labels succeeds, and the inferred predictor types match a
   hand-written expectation (all NOMINAL for German Credit
   categoricals and Car Evaluation; ORDINAL for Balance Scale
   predictors; ORDINAL or CONTINUOUS for German Credit numerics
   depending on cardinality).
3. **Train test.** Training with a fixed engine, depth, minimum child
   size, and seed succeeds and produces a tree with a fingerprint that
   matches a hardcoded value.
4. **Evaluate test.** `evaluate_oos` succeeds and produces Gini, KS,
   and AUC inside a range documented in
   `docs/validation_results_3.6.md`. The range is captured from the
   author's own run and is not a claim about the literature.
5. **Report test.** `get_gains_table` and `get_classification_matrix`
   succeed and produce DTOs with the expected shapes (one row per
   leaf; a K×K matrix for the multiclass datasets).

The exact fingerprint values are computed during 3.6.c and hardcoded
then. This document does not presuppose them.

### 5.3 Fingerprint stability

Fingerprint stability is the operational meaning of "reproducibility"
in TreeGov. If a change to any part of the pipeline silently alters
the fingerprint of a model trained on German Credit with fixed
hyperparameters, the change has altered the model — regardless of
whether the suite still passes.

The integration tests therefore assert the fingerprint value
explicitly. A change to any documented parameter, any engine default,
or any builder detail that affects the fingerprint will fail the test.
This is the desired behaviour: it forces the author to acknowledge,
in a commit, that the change is intentional.

The fingerprint is *not* expected to survive:
- Changes to `class_labels` (they enter the fingerprint).
- Changes to `governance_mode` or `apply_jeffreys` / `pd_floor`.
- Any change to a documented engine parameter.

Each of those is a deliberate model change, and the test failing is
the correct signal.

### 5.4 Why no skip / no subset

The current repository has no `tests/fixtures/` directory. Creating
one and versioning the three CSVs is the simplest possible design and
the only one that keeps the validation self-contained.

Considered and rejected:

- **Download-on-first-test.** Fragile: tests fail without internet,
  and the failure mode is a hard error rather than a skip, which
  trains users to ignore red tests.
- **Subset fixtures.** Discussed in §5.1.
- **Skip if missing.** Same problem.
- **Reference by URL only.** Not reproducible offline; not acceptable
  for an MRM artefact.

## §6. Validation script and report (D6, D8)

### 6.1 Purpose of `scripts/validate_uci.py`

`scripts/validate_uci.py` is a standalone runner that:

1. Loads each normalised dataset from `tests/fixtures/uci/`.
2. Runs the pipeline with a fixed configuration (engine, depth,
   min_child_size, seed) matching the integration tests.
3. Prints the fingerprint, tree structure summary, and metrics for
   each dataset.
4. Writes the results to `docs/validation_results_3.6.md` (overwriting
   the file).

The script is the source of the report. Running it after any
legitimate change to the pipeline regenerates the report; running it
after an *illegitimate* change produces a diff in the report that
forces review.

The script is not part of `pytest`. It is a manual tool, invoked when
the report needs to be refreshed.

### 6.2 Report structure

`docs/validation_results_3.6.md` contains:

- **Metadata.** Date of generation, git commit hash at generation
  time, Python version, engine/seed/depth configuration used.
- **Per dataset:**
  - Source: UCI dataset ID, URL, SHA256 of the source file.
  - Shape: `n_rows`, `n_cols`, target class counts.
  - Inferred predictor types (from `describe_dataset`).
  - Fingerprint of the trained model.
  - Tree summary: number of nodes, number of leaves, max depth.
  - Metrics: Gini, KS, AUC, accuracy (where applicable), Brier, BSS.
  - Gains table (abbreviated): a few representative rows.
- **Cross-dataset observations.** Short paragraphs noting, for
  example, that Car Evaluation's `vgood` class (3.8%) yields a
  near-zero per-class F1, which is expected and is not a bug.
- **Appendix: German Credit code table.** The mapping from the
  original `A11`, `A12`, ... codes to their published descriptions
  from `german.doc`, for readability only.

The report is a narrative artefact, not a raw dump. It is written for
the same audience as the rest of the project's documentation: an MRM
reviewer who wants to understand what was validated and why the
numbers are what they are.

### 6.3 Baseline propio vs literature comparison (D8)

The report distinguishes two things and never mixes them:

**The baseline (quantitative).** The exact metrics obtained by running
the pipeline on the fixture datasets with a documented configuration.
This is a *reproducible baseline*, not a claim about the literature.
Its authority derives from the reproducibility of the pipeline, not
from agreement with any external source.

**The literature comparison (qualitative).** A short paragraph per
dataset situating the baseline in the range typically reported in
the credit-scoring literature, without numerical precision and
without claims of exact agreement. For example:

> The Gini obtained on German Credit in this configuration is
> consistent with the range typically reported for single decision
> trees on this dataset in the credit-scoring literature. Papers
> using ensemble methods report substantially higher values; the
> comparison here is to single-tree methods only.

The paragraph is deliberately vague on numbers. Published results
vary with train/test protocol, cross-validation scheme, feature
selection, and hyperparameter tuning. Claiming a specific numeric
match would be either false or, at best, an accident of matching a
particular author's choices. The report avoids the claim.

**What the report does NOT do.** It does not perform cross-validation
or any other protocol replication. That would require implementing CV
(deferred to Phase 2.1.b) and would open decisions not covered by the
project's design discipline.

## §8. Risks and invariants

### 8.1 Non-negotiable invariants

1. **No changes to `backend_v3/`.** Phase 3.6 validates; it does not
   develop. Any bug found during validation is recorded in
   `docs/audit_log.md` and deferred to a corrective sub-phase.
2. **Fixtures are the ground truth.** The integration tests read only
   from `tests/fixtures/uci/`. They do not depend on internet access,
   on `data/uci/`, or on the fetch script having been run.
3. **Fingerprints are stable across runs.** Given the same fixture
   CSV, the same seed, the same engine, and the same hyperparameters,
   the fingerprint is identical between runs and between machines.
4. **The fetch script is idempotent.** Running it twice on a clean
   workspace produces identical outputs. Running it on a workspace
   with existing outputs either skips them (if hashes match) or
   fails loudly (if they do not).
5. **The existing 416/416 suite is untouched.** Phase 3.6 adds new
   tests; it does not modify existing ones except where the
   `.gitignore` or `pyproject.toml` need updating (neither should).

### 8.2 Risks

1. **UCI changes a source file.** Mitigation: SHA256 verification
   catches it and fails the fetch script. The fixtures remain stable
   because they are versioned independently.
2. **The fixtures absorb a silent error during 3.6.b.** For example,
   if the author normalises German Credit with the target inverted
   (`Good → 1`) but does not notice, the fixture encodes the wrong
   convention. Mitigation: the integration test for German Credit
   asserts the total count per target class (300 in class 1, 700 in
   class 0) as a hand-verified invariant, in addition to the
   fingerprint.
3. **A legitimate future change to the pipeline silently changes the
   fingerprints.** This is not a risk of Phase 3.6 per se, but a
   consequence of fingerprint stability. Mitigation: any such change
   must be documented in `docs/audit_log.md` and the fingerprints in
   the integration tests updated in the same commit. The integration
   tests failing is the correct trigger; the failure is not a bug,
   it is a governance signal.
4. **The report becomes a marketing artefact.** An MRM reviewer could
   read "Gini 0.32 on German Credit" as a claim of quality rather
   than as a reproducibility statement. Mitigation: §6.3 above
   explicitly delineates the two registers, and the report opens
   with a paragraph restating that the baseline is not a claim about
   the literature.
5. **Balance Scale's `R` class (49 rows, 7.8%) proves too small for a
   stable tree.** This is expected and not a bug. Mitigation: the
   integration test verifies the tree structure and the fingerprint,
   not the per-class F1 of the rare class. The report documents the
   low per-class F1 as expected behaviour.
