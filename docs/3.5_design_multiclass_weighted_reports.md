**Purpose.** This document defines the design of Phase 3.5 (multiclass and weighted metrics, reports, and stability monitoring) before any code is written. It is the reference for the implementation sub-phases 3.5.a to 3.5.d, and the audit trail for the design decisions D1 to D20, approved by the author on 13/10/2026
(D1–D14) and on 15/10/2026 (D15–D17 and D18–D20).

## §0. Scope and objective

### 0.1 What 3.5 delivers

Phase 3.5 opens the last three points of the analytical pipeline that still block targets with K > 2 classes, and integrates the multiclass mode (Phases 3.1 and 3.4) with the weighted mode (Phase 3.2).

Concretely:

- **Multiclass validation.** `validation.compute_oos_metrics` accepts K > 2 and returns multiclass generalisations of every discrimination and calibration metric it reports today: Gini (Hand & Till 2001), AUC (pairwise averaged), KS (worst-case pairwise), Brier score and Brier skill score (multiclass form, with the 1/2 parity factor approved by decision D12), PR-AUC (micro-average), and ROC data (K one-vs-rest curves plus global points). Hosmer-Lemeshow is blocked by design and returns None with a WARNING (decision D5).
- **Multiclass reporting.** `reporting.build_gains_table` returns a single gains table ordered by the PD of the class of interest, with per-class counts and rates (decision D2). `reporting.build_classification_matrix` returns the full K×K matrix with per-class precision, recall, F1, and event capture rate, plus global accuracy (decision D3). The gains-table discrimination metrics (KS/AUC/Gini) are computed by the same weight-aware routines as compute_oos_metrics, closing the deferred decision §13.7 of design_decisions.md for the multiclass path only (decision D13). The PR-AUC field preserves exact K=2 parity by reporting the target-class binary value for K=2 (decision D14).
- **Multiclass stability.** `Session.evaluate_oot` accepts K > 2. The Gini Drop check works unchanged on top of the new multiclass Gini (decision D9). PSI and CSI are already target-agnostic and need no change.
- **Weighted × multiclass composition.** Every metric above accepts the optional weight vector delivered in Phase 3.2 and weights class masses following the same pattern as Phase 3.2.g (decision D10). With weights equal to None or uniform, results are exactly identical to the unweighted mode.
- **Unblocking.** The explicit K > 2 blocks installed in Phase 3.1.d are removed from the four blocking points (decision D11). The error messages pointing to "Fase 3.5" disappear.

### 0.2 What 3.5 does NOT deliver

- **Continuous regression metrics.** The continuous-target path (variance impurity, RMSE-style evaluation) is not touched. Phase 3.5 concerns classification targets with K ≥ 2 classes only.
- **Other problem domains.** Ordinal classification, ranking, and cost-sensitive learning are out of scope. The multiclass generalisations chosen here assume a nominal, unordered target, consistent with the tree layer delivered in Phase 3.1.
- **Multiclass Hosmer-Lemeshow.** Blocked by design (decision D5), not merely deferred. The Fagerland, Hosmer and Bofin (2012) extension was evaluated and rejected on complexity-versus-value grounds.
- **GUI redesign.** Sub-phase 3.5.d wires the new DTOs into the existing panels and adapts the wizard where strictly necessary, but the aesthetic redesign of the tree viewer and reports panel (the eight UX findings H1–H8 recorded on 13/10/2026 in `docs/roadmap.md`, Deferred section) is explicitly out of scope for 3.5.
- **Changes to engines, TreeBuilder, or the fingerprint.** The tree layer is complete since Phases 3.1 and 3.4. Phase 3.5 touches only the downstream consumers.

### 0.3 Why this scope

The scope closes the last functional gap of the Phase 3 arc: after 3.1 (tree layer), 3.2 (weighting), 3.3 (population categories), and 3.4 (engines), a user can train a multiclass weighted tree but cannot evaluate it, report it, or monitor it. Leaving the pipeline half-open would force analysts to export predictions and compute metrics by hand — precisely the kind of unaudited side computation that the project's MRM discipline exists to prevent. The scope is deliberately limited to the three blocking points plus their Session entry points, with no engine or structural changes, so that the Phase 3.1 parity invariant (binary behaviour identical to pre-3.1) can be extended into a Phase 3.5 parity invariant (binary behaviour identical to pre-3.5) with minimal surface area.

## §1. Current state

### 1.1 The blocks installed by Phase 3.1.d

Phase 3.1 opened the tree layer to K ≥ 2 classes but deliberately left the downstream analytical layer binary. The rationale, recorded in `docs/3.1_design_multiclass.md` §5, was coherence: a multiclass tree evaluated with binary metrics would produce silently wrong numbers (for example, a Gini computed on the target-class probability alone, ignoring the rest of the class distribution). Rather than ship half-correct generalisations, Phase 3.1.d installed explicit fail-fast blocks and deferred the real work to Phase 3.5.

There are three blocking points, all raising `ValueError` with a message stating that multiclass is not implemented in Phase 3.1 and is planned for Phase 3.5:

1. **`validation.compute_oos_metrics`.** Entry point for all OOS/OOT discrimination and calibration metrics. Raises when the model's number of classes K exceeds 2.
2. **`reporting.build_gains_table` and `reporting.build_classification_matrix`.** Entry points for the two report DTOs consumed by the reports panel and the HTML export. Both raise when K exceeds 2.
3. **`Session.evaluate_oot`.** The session-level OOT evaluation raises when K exceeds 2, because it internally relies on the two points above (metrics plus the OOS/OOT comparison report). Note that `Session.evaluate_oos`, `Session.get_gains_table`, and `Session.get_classification_matrix` are thin propagators over points 1 and 2; they inherit the block transitively rather than raising on their own.

### 1.2 Interaction with the weighted mode

Phase 3.2 extended all three blocking points with an optional keyword-only weight vector (Phase 3.2.g), including weighted variants of every binary metric and eleven additional weighted fields on the gains table DTO. Two decisions from that phase are directly relevant here:

- **Deferred weighting of the gains-table discrimination metrics** (`docs/design_decisions.md` §13.7): the KS/AUC/Gini stored on the gains-table result DTO are currently computed unweighted even when weights are present, to avoid duplicating logic already centralised in `validation.py`. Phase 3.5 revisits this point as part of the multiclass rewrite: the discrimination metrics attached to the multiclass gains table are computed by calling the same multiclass, weight-aware routines as `compute_oos_metrics`, closing the deferred decision for the multiclass path. Decision D13 (approved 13/10/2026) approves closing this deferred item for the multiclass path only. The binary path remains as-is.

  **Deferred asymmetry note (15/10/2026).** D13 closes the deferred §13.7 for the multiclass path only. Consequently, the binary path of build_gains_table keeps _discrimination_metrics unweighted even when it receives weights; the multiclass path will call validation.compute_oos_metrics (which does weight). The asymmetry is deliberate and respects the phase's non-negotiable invariant (K = 2 with weights None or uniform, bit-for-bit identical to pre-3.5). No new decision is introduced: this is an explicit consequence of D13.
- **Hosmer-Lemeshow scales linearly with total weight mass** (`docs/design_decisions.md` §13.8): recorded behaviour, not a bug. Irrelevant for the multiclass path because HL is blocked there (decision D5); remains in force for the binary path.

### 1.3 What already works on K > 2

The following components already operate correctly on multiclass weighted models and need no change in 3.5:

- `Session.train` (all four engines, since Phase 3.4).
- `predict_pd` (returns the 2D array of shape n_rows × K, with the canonical class ordering of Phase 3.1: target class at index 0).
- `predict_leaf_assignment`, pruning, and the fingerprint.
- PSI of leaves and CSI of covariates in `stability.py`, which are target-agnostic by construction (verified by the test referenced as `test_stability_agnostic_to_k`).
- Population filtering (Phase 3.3), which composes orthogonally with both multiclass and weighting.

## §2. Validation multiclass — compute_oos_metrics

This section specifies the multiclass generalisation of each metric returned by `compute_oos_metrics`. All formulas are given in prose; the implementation must cite the same references in its docstrings. Decisions D1, D4, D5, D6, D7, and D8 are defined here.

### 2.0 Input contract of compute_oos_metrics (decision D15)

The input p of compute_oos_metrics accepts two forms, under a literal contract that must appear verbatim in the function's docstring because compute_oos_metrics is a public signature. The 1D form is the classic binary path: y is encoded 0/1 and p[i] is the probability of the event class (index 0 of the canonical pd_final vector in each leaf). The 2D form has shape (n, K). For K = 2 in 2D form, the function internally reduces to column 0 and executes the binary path — this is the parity shortcut required by D12 and D14: any caller passing 1D for K = 2 today obtains the same result, bit for bit, as a caller passing 2D with K = 2. For K greater than 2, the 2D form is mandatory and y must be a 1D vector of labels in the set {0, 1, ..., K−1}, where label c corresponds to column c of p; the caller is responsible for reordering the classes to the canonical order before calling (explicit contract, see §2.8). This dispatch on the shape of p preserves the bit-for-bit parity of the binary path without touching existing callers (Session.evaluate_oos keeps passing 1D for K = 2) and makes the semantics of the 2D form explicit without extra parameters such as class_order. Rationale: the alternative of always receiving 2D would have forced touching every existing K = 2 test and would have broken the signature parity with pre-3.5.

### 2.1 Multiclass Gini — Hand & Till (decision D1)

The multiclass Gini is computed from the pairwise AUC generalisation of Hand and Till (2001). For each unordered pair of classes (i, j) with i < j, consider only the observations belonging to class i or class j. Let A(i, j) be the probability that a randomly chosen member of class j has a lower estimated probability of belonging to class i than a randomly chosen member of class i, computed from the i-th column of the predicted probability matrix; let A(j, i) be the symmetric quantity with the roles reversed. The pair contribution is the average of A(i, j) and A(j, i). The multiclass AUC, denoted M by Hand and Till, is the arithmetic mean of these pair contributions over all K·(K−1)/2 unordered pairs.

The multiclass Gini is then Gini = 2·M − 1, applying the project's standing credit-scoring convention (Gini = 2·AUC − 1, already recorded in `docs/roadmap.md` under Recorded architectural decisions).

**Parity property.** For K = 2 there is exactly one pair, and the pair contribution equals the standard binary AUC of the target class. The formula therefore reduces exactly to the current binary Gini. This is not an approximation: with one pair, M equals the binary AUC by construction, so the K = 2 result is bit-identical to the pre-3.5 computation given identical inputs.

**Citation.** Hand, D.J. and Till, R.J. (2001). A simple generalisation of the area under the ROC curve for multiple class classification problems. Machine Learning, 45(2), 171–186.

### 2.2 Pairwise AUC computation and tie handling

Each pairwise AUC is computed with the direct pair-counting formula already used in the binary path since Phase 3.2.g: concordant pairs count one, tied pairs count one half, discordant pairs count zero, normalised by the product of the two class masses (counts, or weight sums in the weighted mode). Reusing the same pair-counting kernel for the binary and multiclass paths is what makes the K = 2 parity a structural property rather than a numerical coincidence.

### 2.3 Multiclass KS — worst-case pairwise (decision D4)

There is no canonical extension of the Kolmogorov-Smirnov statistic to K classes. The design adopts the most conservative and MRM-relevant choice: the reported KS is the minimum of the pairwise KS values across all unordered pairs of classes. Since a higher KS means better discrimination, the minimum is the worst case — the number an MRM reviewer would use to challenge the model.

For K = 2 there is exactly one pair, so the reported value reduces exactly to the current binary KS.

### 2.4 Hosmer-Lemeshow — blocked by design (decision D5)

The Hosmer-Lemeshow calibration test is intrinsically binary: it groups observations by predicted probability of one event class and compares observed versus expected event counts. The multinomial extension of Fagerland, Hosmer and Bofin (2012) is technically viable but introduces a second grouping dimension (per-class deciles), a different reference distribution, and interpretive subtleties that add no operational value for the analyst in the current GUI: the calibration story of a multiclass tree is told by the per-class observed-versus-predicted rates already visible in the gains table.

Decision: in the multiclass path, the HL fields of the metrics DTO are set to None, a WARNING is logged explaining that HL is binary-only by design and pointing to the Fagerland reference, and no statistic is computed. The binary path is untouched.

**Citation.** Fagerland, M.W., Hosmer, D.W. and Bofin, A.M. (2012). Multinomial goodness-of-fit tests for logistic regression models. Statistics in Medicine, 31(30), 4238–4253.

(decision D16.) The type and validation effect of the HL block in multiclass was not specified in D5. This refinement makes it concrete: in multiclass mode (K greater than 2) the fields hl_stat, hl_df and hl_p of the OOSMetrics DTO become None and a WARNING is logged citing Fagerland 2012; consequently, the types of the three fields change from float, int and float to float or None, int or None and float or None respectively. The field hl_groups keeps type int because it reflects the caller's n_groups input parameter, which remains mandatory. The validations n_groups greater than or equal to 3 and n_groups times 5 less than or equal to n are skipped when K is greater than 2, because HL is not computed; they remain in full force for K = 2. Rationale: the substantive decision (blocking HL in multiclass) does not change; what is closed is the grey zone of types and validations that D5 did not specify.

### 2.5 Multiclass Brier score (decision D6)

The multiclass Brier score is the quadratic scoring rule summed over the true-class indicator: Brier = (1/(2N)) · Σ over observations i and classes k of (y_ik − p_ik)², where y_ik is 1 if observation i belongs to class k and 0 otherwise, and p_ik is the predicted probability assigned to class k for observation i.

**The factor 1/2 (decision D12).** The raw quadratic sum over all K classes equals, for K = 2, exactly twice the conventional binary Brier score (because both the event and non-event terms contribute the same squared error). The design includes the factor 1/2 so that the K = 2 case reduces exactly to the binary Brier score the project already reports. This normalisation is standard in the forecasting literature and preserves the parity invariant without special-casing K = 2 in the code. This factor was audited and approved as decision D12 on 13/10/2026, because its absence would break the parity invariant for K=2.

**Multiclass Brier skill score.** The skill score keeps its binary form: BSS = 1 − Brier_model / Brier_reference, where the reference is the climatological forecaster that predicts the empirical class frequencies (the class priors of the evaluation sample) for every observation. In the weighted mode, both the model and reference scores use weighted masses, and the reference frequencies are the weighted class frequencies.

### 2.6 Multiclass PR-AUC — micro-average (decisions D7 and D14)

Precision-recall analysis generalises to K classes by micro-averaging: the K per-class binary problems are pooled into a single binary problem in which each (observation, class) pair contributes one example, positive when the class equals the true class of the observation and negative otherwise, scored by the predicted probability of that class. The PR curve and its area are computed on this pooled problem with the same stepwise (non-interpolated) integration used in the binary path, consistent with Davis and Goadrich (2006), already cited in `docs/methodology.md` §8.10.

For K = 2 the pooled problem contains, for each observation, the target-class pair (identical to the binary problem) plus the mirror pair for the other class. The design keeps exact K = 2 parity by reporting, for K = 2, the same target-class PR-AUC as the pre-3.5 binary path (decision D14, audited and approved on 13/10/2026); the micro-average formula is applied as stated for K > 2, and the K = 2 shortcut is documented in the implementation docstring so that the parity invariant holds bit-for-bit. The weighted mode weights each pooled example by the observation's weight.

**Citation.** Davis, J. and Goadrich, M. (2006). The relationship between Precision-Recall and ROC curves. Proceedings of the 23rd International Conference on Machine Learning (ICML), 233–240.

### 2.7 Multiclass ROC data (decision D8)

The metrics DTO exposes, for the multiclass path, K one-vs-rest ROC curves — one per class, treating that class as positive and all others as negative — in addition to the global ROC points already produced today. Each one-vs-rest curve is computed with the same threshold sweep as the binary ROC. This gives the GUI enough data to draw per-class curves without re-deriving them downstream, and keeps the binary payload unchanged for K = 2.

(decision D17.) §9.2 of the design requires the DTO to expose the per-pair values so the reviewer can see which pair dominates the worst-case KS; D17 makes the form concrete. The OOSMetrics DTO gains three new fields at the end of its definition, all with empty defaults so existing constructors are not broken (for example, the _oos_stub stub in tests/test_reporting.py). The three fields are: ks_pairs, a tuple of tuples of the form (i, j, ks) for each pair i less than j, ordered ascending by i and then by j; auc_pairs, a tuple of tuples of the form (i, j, auc) with the same ordering; and roc_per_class, a tuple of K entries, each one a tuple of points (fpr, tpr, threshold) with the same structure as today's binary roc_points, corresponding to the K one-vs-rest ROC curves of §2.7. For K = 2 the three fields are populated: ks_pairs and auc_pairs hold a single tuple ((0, 1, val),) and roc_per_class holds two entries (one per class). The binary roc_points payload does not change in any case. Rationale: D8 specified that the DTO must expose the K one-vs-rest curves but did not name the field; D17 closes that form.

### 2.8 Weighted composition (decision D10)

Every metric in this section accepts the optional weight vector following the pattern established in Phase 3.2.g: counts become weight sums, empirical frequencies become weighted frequencies, and the pairwise AUC uses the direct pair formula with half credit on ties over weighted masses (Heeringa, West and Berglund 2010, §5.3). The known scaling behaviours recorded in Phase 3.2 carry over unchanged: statistics that are ratios (AUC, Gini, KS, Brier after normalisation, BSS) are scale-invariant; statistics that accumulate mass would scale, and none is introduced here. With weights equal to None or to a uniform vector, every result is exactly identical to the unweighted mode.

**Citation.** Heeringa, S.G., West, B.T. and Berglund, P.A. (2010). Applied Survey Data Analysis. Chapman & Hall/CRC, §5.3.

## §3. Reporting multiclass — build_gains_table and build_classification_matrix

### 3.1 Gains table structure (decision D2)

The multiclass gains table is a single table, not K separate tables. Rows are the tree leaves (or score segments) ordered by the predicted probability of the class of interest, ascending, following the project's bureau convention already used in the binary table and consistent with the canonical class ordering of Phase 3.1 (the target class occupies index 0 of the class-labels tuple).

Each row carries the following columns:

- Leaf/segment label (the existing label column).
- Predicted PD of the class of interest for the segment.
- Total N of the segment (physical row count).
- N per class: one column per class, in canonical order, with the physical count of observations of each class in the segment.
- Observed event rate of the class of interest within the segment.
- Cumulative and decumulative blocks, mirroring the binary table: cumulative N, cumulative N per class, cumulative event rate of the class of interest, and the corresponding decumulative columns.

In the weighted mode, the Phase 3.2 pattern applies: the table carries the parallel weighted columns (weighted N, weighted N per class, weighted rates, weighted cumulative and decumulative blocks), and with weights equal to None the weighted columns coincide exactly with their physical counterparts, as already verified for the binary table in Phase 3.2.g.

**Header metrics.** The discrimination metrics attached to the gains-table result (KS, AUC, Gini) are computed in the multiclass path by the same routines specified in §2 — that is, Hand & Till AUC/Gini and worst-case pairwise KS — and, when weights are present, they are the weighted variants. This closes, for the multiclass path, the decision deferred in `docs/design_decisions.md` §13.7; the binary path remains as it is. (Decision D13.)

(decision D18.) The pre-validation of routable rows (_validated_routed in reporting.py) currently checks that y is binary. With K greater than 2, y carries labels in {0, 1, ..., K−1}. The adopted decision is to parameterise the helper with an optional n_classes: with n_classes=None (default, pre-3.5 behaviour) it requires binary y; with n_classes=K it requires y in the range {0, 1, ..., K−1}. The binary path keeps the current strict validation; the multiclass path extends it without duplicating the helper. Alternatives considered and rejected: (a) removing the y validation from the helper and delegating it to each caller (breaks the contract of _validated_routed as the single guardian of the input); (b) creating a parallel _validated_routed_multiclass (duplicates routing logic for the sake of a few characters of difference).

(decision D20.) build_gains_table does not currently impose a minimum number of routable rows, but compute_oos_metrics requires n_groups greater than or equal to 3 and n_groups * 5 less than or equal to n (minimum 50 rows for the default n_groups=10, minimum 15 rows for the minimum n_groups=3). If the multiclass path called compute_oos_metrics with the default n_groups, any gains table with fewer than 50 routable rows would raise ValueError. The adopted decision is for the multiclass path to compute n_groups adaptively with the same formula Session.evaluate_oot uses for OOT: n_groups = min(10, max(3, n // 5)), where n is the number of routable rows. If n is less than 15, the ks, auc and gini fields of GainsTableResult are returned as None without calling compute_oos_metrics; the remaining fields (counts, bad_rate, lift, w_*) are populated normally. This pattern is already established in Session.evaluate_oot and Session.evaluate_oos (see g_eff); D20 applies it to reporting. Alternative considered and rejected: relaxing the n_groups validation of compute_oos_metrics (would break the Cochran-5 rule that the binary path has preserved since Phase 1.2).

### 3.2 Classification matrix (decision D3)

The multiclass classification matrix is the full K×K contingency table of true class (rows) versus predicted class (columns), with the canonical class ordering on both axes. Beyond the raw cells, the DTO reports, per class:

- **Precision**: for class k, the diagonal cell divided by the column total of k.
- **Recall**: for class k, the diagonal cell divided by the row total of k. Recall of the class of interest is the quantity the binary path already reports.
- **F1**: the harmonic mean of precision and recall of class k.
- **Event capture rate**: an alias of recall for the class of interest. The two fields report the same value, mirroring the bad_capture_rate = recall convention of the binary path.

The DTO additionally reports **global accuracy**: the trace of the matrix divided by the total N.

For K = 2 the per-class metrics and the K×K layout contain, as a special case, every field the binary classification-matrix DTO reports today (true positives, false positives, and so on), and the numerical values coincide exactly with the pre-3.5 binary computation at the same classification threshold. The threshold mechanism itself is unchanged: observations are assigned to the class of maximum predicted probability, and for K = 2 the configurable threshold on the target-class probability continues to govern the assignment exactly as before.

In the weighted mode the matrix carries the parallel weighted cells and weighted per-class metrics, following the same parallel-fields pattern as Phase 3.2.g.

**Citation.** Breiman, L., Friedman, J.H., Olshen, R.A. and Stone, C.J. (1984). Classification and Regression Trees. Wadsworth. (The per-class error decomposition follows the standard misclassification-cost accounting of C&RT, generalised to K classes.)

### 3.3 DTO compatibility with existing consumers

The current frontend (reports panel and HTML export) consumes the binary DTOs. The multiclass DTOs are designed as supersets: every field the binary consumer reads keeps its name, type, and meaning, and the multiclass-only fields are additive (per-class count columns, per-class precision/recall/F1 vectors, K ROC curves). A K = 2 model therefore drives the existing panels without modification, which is what makes the frontend compatibility invariant of §9 testable.

(decision D19.) The multiclass path of reporting.py materialises with two architectural commitments documented together. First, direct import of validation: reporting.py imports compute_oos_metrics from validation.py without going through TYPE_CHECKING and without duplicating the discrimination logic. The prior dependency check confirms there is no cycle (validation.py does not import reporting.py today, and there is no indirect chain that would introduce one). The private helper _discrimination_metrics is kept for the binary path (the D13 asymmetry); the multiclass path bypasses it by calling compute_oos_metrics. Second, a superset ClassificationMatrix DTO: build_classification_matrix (binary, no signature change) and build_classification_matrix_multiclass (new) return the same ClassificationMatrix type, extended with new fields at the end with empty defaults. The inherited binary fields (tp, tn, fp, fn, precision, recall, f1, bad_capture_rate, n_good, n_bad) are populated in the multiclass path with the class of interest (index 0) as "positive" and the rest as "negative", preserving the semantics the binary panel consumer already reads. The accuracy field is populated in both modes (K = 2 and K greater than 2): for K = 2 it is the trace of the 2x2 matrix divided by n; for K greater than 2 it is the trace of the K x K matrix divided by n. The ClassificationMatrix docstring must reflect both rules. New DTO fields (all with empty defaults): confusion_matrix (K x K), n_per_class (K), precision_per_class, recall_per_class, f1_per_class, accuracy; and their weighted counterparts w_confusion_matrix, w_precision_per_class, w_recall_per_class, w_f1_per_class, w_accuracy.

## §4. Stability multiclass — Gini Drop

### 4.1 No structural change (decision D9)

The Gini Drop check compares the Gini on the training partition against the Gini on the OOT cohort: drop = (Gini_train − Gini_X) / Gini_train, where X is the cohort under evaluation. The formula does not change. The only thing that changes is the Gini that feeds it: with K > 2, both Gini values are the Hand & Till multiclass Gini of §2.1, computed on the respective cohorts (and, when weights are present, with each cohort carrying its own weights, per the Phase 3.2.h convention).

### 4.2 PSI and CSI need nothing

The leaf-PSI and covariate-CSI routines operate on distributions over leaves and over covariate values respectively; neither touches the target's class structure. This is already verified by the existing test referenced as `test_stability_agnostic_to_k`, which exercises the stability report with K > 2 fixtures for the target-agnostic components. Phase 3.5 only removes the block that prevented `Session.evaluate_oot` from reaching these routines with a multiclass model.

## §5. Session changes

### 5.1 Unblocking (decision D11)

The K > 2 blocks are removed from the four session-level entry points:

- `Session.evaluate_oos` — propagates to the unblocked `compute_oos_metrics` with the test partition (and its weights, when present).
- `Session.evaluate_oot` — the explicit K > 2 raise is removed; the method now flows through metrics, gains table, and stability report exactly as in the binary path.
- `Session.get_gains_table` — propagates to the unblocked `build_gains_table`.
- `Session.get_classification_matrix` — propagates to the unblocked `build_classification_matrix`.

The error messages referencing "Fase 3.1" and "Fase 3.5" disappear from the codebase. A grep for the message text after 3.5.a–3.5.c must return no hits.

### 5.2 No change elsewhere in Session

`fix_spec`, `partition`, `load_oot`, `train`, `reset_to_data_loaded`, and the population machinery are untouched. The session already carries everything the downstream layer needs: the model with its K classes and canonical ordering, the partition indices, and the per-partition weight caches populated since Phase 3.2.f.

## §6. Fingerprint

No changes. The `params_fingerprint` already captures `class_labels` and the number of classes since Phase 3.1 (see `docs/3.1_design_multiclass.md` §7), and the weighting mode since Phase 3.2.e (`weighted`, `weight_col`, `min_child_weight`). Phase 3.5 changes no hyperparameter, no engine behaviour, and no tree structure; it only changes how an already-trained model is evaluated and reported.

Two consequences, stated explicitly for the audit trail:

- Two K = 3 trees trained on the same data with the same hyperparameters share the same fingerprint, regardless of whether their reports were generated before or after Phase 3.5. Evaluation is not a model parameter.
- Two models that differ only in K necessarily differ in `class_labels`, hence in fingerprint. There is no collision risk introduced by this phase.

## §7. Tests plan

### 7.1 New unit tests, with hand-verified values

Each new test computes its expected values by hand (or by an independent derivation recorded in the test docstring), following the project's verification discipline:

- **`tests/test_validation.py`.** A small K = 3 fixture (three classes with known scores) where the Hand & Till AUC is computed pair by pair by hand; the worst-case pairwise KS identified by hand; the multiclass Brier and BSS checked against manual quadratic sums with the 1/2 normalisation; the micro-average PR-AUC checked on the pooled problem; HL asserting None plus the logged WARNING; the K one-vs-rest ROC curves checked for shape and endpoints.
- **`tests/test_reporting.py`.** A K = 3 gains-table fixture asserting column presence, canonical ordering, ascending PD of the class of interest, and per-class count columns summing to the row total; a K = 3 classification-matrix fixture asserting per-class precision/recall/F1 and global accuracy against hand computation at a fixed threshold.
- **`tests/test_stability.py`.** Gini Drop on a K = 3 fixture with the multiclass Gini feeding the unchanged drop formula.
- **`tests/test_session_state.py`.** End-to-end unblocking: `evaluate_oos`, `evaluate_oot`, `get_gains_table`, and `get_classification_matrix` succeed on a K = 3 model, and the absence of the old "Fase 3.5" error text is asserted.

### 7.2 Parity invariants

- **K = 2 parity.** Once unblocked, every multiclass result with K = 2 must coincide exactly with the binary results produced before Phase 3.5: Gini, AUC, KS, Brier, BSS, PR-AUC, ROC, gains-table columns, classification-matrix fields. This is the phase's central invariant and is tested with dedicated parity tests reusing the existing binary fixtures.
- **Weight parity.** Every multiclass metric with weights equal to None must equal the same metric with a uniform weight vector, and both must equal the unweighted computation.

### 7.3 Weighted × multiclass tests

Fixtures combining K = 3 with non-trivial weights: per-class weighted masses checked by hand; weighted pairwise AUC checked by the direct pair formula with half credit on ties; scale-invariance of ratio statistics under multiplication of all weights by a positive constant (the pattern established in Phase 3.2).

## §9. Risks and invariants

### 9.1 Non-negotiable invariants

1. **K = 2 parity.** With K = 2, and weights equal to None or uniform, every metric, table, and matrix produced after Phase 3.5 is numerically identical to its pre-3.5 binary counterpart. Tested by the dedicated parity tests of §7.2.
2. **Fingerprint unchanged.** No new fingerprint entries, no structural change. Evaluation is not a model parameter (§6).
3. **Frontend compatibility.** The binary consumers (reports panel, metrics panel, HTML export) keep reading the same fields with the same meaning; the multiclass DTOs are additive supersets (§3.3). A K = 2 model drives the existing GUI without modification.

### 9.2 Risks

1. **Hand & Till Gini may look surprisingly low with K > 2 and imbalanced classes.** The pairwise averaging dilutes strong discrimination on the majority pair with weak discrimination on minority pairs. An analyst migrating from binary models may read a Gini of 0.25 as poor when it is respectable for K = 4. Mitigation: the metrics panel and the methodology document state the reference (Hand & Till 2001) next to the number, and the K one-vs-rest ROC curves (§2.7) give the per-class view that the scalar hides.
2. **The HL block leaves a calibration gap in the multiclass path.** There is no goodness-of-fit test for K > 2 in the product. Mitigation: the WARNING logged with the None result (§2.4) states the design reason and the Fagerland reference; the per-class observed-versus-predicted rates in the gains table provide the operational calibration view; the decision is reversible in a future phase if an auditor formally requires a multinomial calibration test.
3. **Worst-case pairwise KS can be dominated by a rare pair.** With K > 2 and a tiny class, the worst pair may reflect small-sample noise rather than model weakness. Mitigation: the reported DTO keeps the per-pair values accessible so the reviewer can see which pair drives the worst case; the documentation recommends reading KS alongside the gains table's per-class counts.
