## §0. Contexto
La Fase 4.0 busca llevar el modelo entrenado fuera de TreeGov, hacia sistemas legados de scoring (bases de datos SQL o scripts de Python). El reto principal es que el `TreeModel` no contiene la lógica de imputación de nulos. Si exportamos una regla `IF edad <= 40`, fallará con los valores nulos.

## §1. Decisiones de Arquitectura

| ID | Decisión | Justificación |
|---|---|---|
| **D1** | Nuevo módulo `backend_v3/exporters.py`. | Sala limpia: `frontend_v3` no genera código, solo muestra y guarda. |
| **D2** | Las funciones de exportación recibirán el `TreeModel` y el `ImputationSpec`. | El `ImputationSpec` ya existe en `backend_v3/imputation.py`. Necesitamos inyectarlo para generar el `COALESCE` en SQL y el diccionario de reemplazo en Python. |
| **D3** | SQL ANSI puro con `CASE WHEN` anidado. | Compatibilidad universal con cualquier motor (Oracle, SQL Server, PostgreSQL). Sin funciones propietarias. |
| **D4** | Python puro sin dependencias (`numpy`, `pandas`). | El script exportado debe poder pegarse en un sistema legado sin necesidad de instalar librerías científicas. |
| **D5** | Incluir el `params_fingerprint` como comentario en el encabezado del código exportado. | Trazabilidad MRM: el auditor sabe exactamente qué modelo generó ese código. |

## §2. Plan de Sub-fases
- **4.0.a**: Backend de exportación SQL y Python (`exporters.py` + tests).
- **4.0.b**: Exportación de reglas legibles (Markdown/JSON).
- **4.0.c**: Integración en la GUI (botones de exportación en el menú Archivo).

## §3. Invariantes
- Paridad de predicción: el código exportado debe devolver exactamente el mismo `pd_final` que el backend para las mismas filas.
- Cero dependencias externas en el código generado.
- El código debe ser legible y auditable por un humano.
